## 4. Стратегия тестирования

Один и тот же сценарий не требуется повторять на каждом уровне. Уровень выбирается по риску и цене отказа.

| Уровень | Объект | Зависимости | Основная цель |
|---|---|---|---|
| Unit | Функция или store | Нет либо управляемый двойник | Быстро локализовать правило и ветвь. |
| HTTP integration | Express-приложение | Настоящий HTTP, fake store | Проверить middleware, статусы, заголовки и JSON. |
| DB integration | PostgreSQL-store | Настоящая отдельная база | Проверить SQL, типы, ограничения и драйвер вместе. |

Примеры выбора:

- граница `parsePositiveId` — unit;
- `Content-Type`, 405 и CORS — HTTP integration;
- соответствие `category_id AS "categoryId"` на настоящем драйвере — DB integration;
- поведение React в браузере — за пределами обязательного набора ПР13.

Сначала составляется карта рисков. Для каждого риска указываются:

1. что может нарушиться;
2. на каком минимальном уровне это обнаруживается;
3. исходное состояние;
4. действие;
5. наблюдаемый результат;
6. очистка состояния.

Тест без наблюдаемого результата не проверяет поведение. Запуск кода только ради покрытия недостаточен.

## 5. Устройство теста

Используется схема Arrange → Act → Assert:

```js
test('описание наблюдаемого поведения', async () => {
  // Arrange: вход и зависимости.
  const store = createFakeStore();

  // Act: одно проверяемое действие.
  const task = await store.getTask(4);

  // Assert: значимый результат.
  assert.equal(task.id, 4);
});
```

Название описывает контракт, а не реализацию. `работает`, `test1` или имя функции без ожидаемого поведения недостаточны.

Правила набора:

- один тест не зависит от результата другого;
- значения id берутся из результата, если они назначаются системой;
- асинхронный вызов обязательно `await`-ится или возвращается;
- для ожидаемого исключения применяются `assert.throws` или `assert.rejects`;
- проверяется тип и код ошибки, а не только факт любого отказа;
- сервер, pool и checked-out client закрываются в `finally`;
- пароль и полный текст DB-ошибки не печатаются в тестовом выводе.

## 6. Модульные тесты

### 6.1. Конфигурация

В `tests/unit/config.test.js` завершить три TODO:

- отсутствующий и пробельный `DATABASE_URL`;
- нечисловой порт и границы 1024–65535;
- допустимые только строки `true` и `false` для debug reset.

Тесты передают объект окружения напрямую в `readConfig(env)`. Реальный `process.env` менять не требуется: это уменьшает связанность и исключает влияние машины.

Проверяется собственное сообщение приложения, но пароль из тестовой строки не должен попадать в текст ошибки.

### 6.2. Разбор query и валидация тела

В `tests/unit/validation.test.js` завершить четыре TODO:

- `null`, массив, строка и число вместо JSON-объекта;
- обязательные и неизвестные поля POST;
- пустой PATCH и несуществующая категория;
- границы title, priority, completed и categoryId.

Один тест может использовать таблицу случаев, если все случаи проверяют одно правило. При отказе полезно передавать значение как третий аргумент assert, чтобы вывод показывал конкретный случай.

Не следует сравнивать весь русский текст ошибки, если контрактом являются `status`, `code` и поля `details`. Полное строковое сравнение делает тест хрупким при редакционной правке сообщения.

### 6.3. Query builders

В `tests/unit/query-builders.test.js` завершить четыре TODO:

- экранирование `%`, `_` и `\`;
- отсутствие пользовательского `q` в SQL-тексте;
- сохранение boolean `false` в UPDATE;
- отказ для пустого и неизвестного набора изменений.

Проверяются одновременно `text` и `values`. Тест, который сравнивает только количество параметров, не обнаружит их перестановку.

SQL можно нормализовать, заменив серии пробелов одним пробелом. Не требуется привязывать тест к отступам и переводам строк. При этом необходимо проверить значимые фрагменты: порядок `$1...$n`, `ESCAPE`, WHERE, RETURNING и алиас.

### 6.4. Store и scripted pool

`scriptedPool` не является базой. Он:

- записывает запросы;
- выдаёт заранее подготовленные `rows` и `rowCount`;
- может выбросить заданную ошибку.

Это позволяет быстро проверить оркестрацию без сети и процесса PostgreSQL.

В `tests/unit/store.test.js` завершить TODO транзакционного отказа:

1. client успешно выполняет BEGIN и первую команду;
2. следующая команда выбрасывает исходную ошибку;
3. store выполняет ROLLBACK;
4. `release()` вызывается ровно один раз;
5. исходная ошибка пробрасывается вызывающему коду.

Тест успешного COMMIT не заменяет тест ROLLBACK: это разные ветви с разным риском утечки подключения и частичной записи.

## 7. HTTP-интеграционные тесты

`tests/support/http.js` запускает настоящее Express-приложение на порту `0`. Операционная система назначает свободный порт, поэтому тесты не конфликтуют с локальным 5505 и параллельными процессами.

`tests/support/fake-store.js` хранит небольшой детерминированный набор в памяти. Он не проверяет SQL, но позволяет проверить маршруты, middleware и HTTP-контракт.

В `tests/integration/api.test.js` завершить пять TODO:

1. неверный media type, пустое тело и сломанный JSON;
2. неизвестное поле и отсутствующая категория без частичного изменения;
3. 405 с `Allow` и OPTIONS с CORS;
4. безопасное отображение SQLSTATE 23503 и 08006;
5. удаление записи между `requireTask` и UPDATE.

HTTP-тест должен наблюдать то, что видит клиент:

- статус;
- JSON-конверт;
- заголовки;
- пустое тело 204;
- отсутствие внутренних деталей.

Прямой вызов route handler с искусственными `req`/`res` не заменяет проверку цепочки Express, потому что пропускает маршрутизацию, парсер тела, CORS и финальный error middleware.

### Проверка отсутствия утечки

Для DB-ошибки создать store, метод которого выбрасывает:

```js
Object.assign(new Error('database detail'), { code: '23503' })
```

В ответе должны отсутствовать `database detail` и `23503`, но должен присутствовать публичный код API. Аналогично проверяется ошибка соединения класса 08.

## 8. Тест реальной базы

`npm test` и `npm run quality` специально не обращаются к PostgreSQL. Они должны быть быстрыми, детерминированными и доступными без локального секрета.

DB-проверка запускается отдельно:

```bash
npm run test:db
```

Для неё нужен локальный `.env`:

```dotenv
DATABASE_URL=postgresql://tip_app:CHANGE_ME@127.0.0.1:5432/tip_tasks_test
```

Используется **отдельная учебная база**, поскольку тест вызывает reset и изменяет строки. Общую, рабочую или чужую базу указывать нельзя.

DB-тест:

- проверяет соединение;
- восстанавливает seed;
- создаёт, читает, изменяет и удаляет запись;
- в `finally` снова восстанавливает исходный набор;
- закрывает pool даже при ошибке assert.

Отсутствующий `DATABASE_URL` приводит к fail, а не к skip. Иначе обязательная интеграционная проверка могла бы незаметно считаться успешной.

Автоматическая очистка через `finally` не является абсолютной гарантией: процесс может быть принудительно завершён. После аварии состояние базы проверяется вручную.

## 9. Покрытие

Node.js 24 собирает покрытие встроенным тестовым раннером. В `package.json` заданы:

```text
lines >= 85%
functions >= 85%
branches >= 75%
```

Команда:

```bash
npm run test:coverage
```

Из отчёта исключены `src/server.js` и `src/db.js`. Первый содержит процессный запуск и сигналы, второй создаёт настоящий Pool. Их обязательная проверка потребовала бы другого уровня тестов. Исключение документировано и не применяется к основной логике.

Покрытие отвечает на вопрос «какой код выполнялся», но не отвечает «правильно ли он проверен». Следующий тест даёт покрытие и почти не даёт гарантии:

```js
assert.ok(validateTaskInput);
```

Добавлять бессодержательные вызовы ради процента нельзя. Сначала выбирается риск и assert, затем оценивается покрытие. Непокрытая ветвь служит подсказкой, но не автоматически становится обязательным тестом.

После завершения базовых TODO эталонный набор достигает порогов с запасом. Снижать пороги вместо добавления осмысленных сценариев не требуется.

## 10. ESLint и Prettier

### 10.1. Разные задачи инструментов

Prettier отвечает за единообразное представление кода. ESLint находит потенциальные ошибки и нарушения правил: неиспользуемые значения, `var`, нестрогое сравнение, отсутствие фигурных скобок и другие проблемы.

```bash
npm run format:check
npm run lint
```

`format:check` ничего не изменяет и подходит для quality gate. Для исправления форматирования используется:

```bash
npm run format
```

После автоматического исправления необходимо просмотреть `git diff`. Форматтер не подтверждает корректность поведения.

### 10.2. Flat config

`eslint.config.js` использует flat config, рекомендуемый современными версиями ESLint:

- `@eslint/js` recommended;
- Node globals;
- ECMAScript modules;
- дополнительные правила курса;
- исключение `node_modules` и покрытия.

Отключать правило для всего проекта ради одного неудобного места нельзя без объяснения. Сначала исправляется код; точечное отключение допускается только при обоснованной ложной тревоге.

## 11. Запрет ложного зелёного результата

`test.todo`, `test.skip` и `test.only` полезны во время разработки, но опасны в итоговом наборе:

- `todo` выполняется, но его отказ не делает процесс неуспешным;
- `skip` не выполняется;
- `only` может оставить большую часть набора вне запуска.

Проверка:

```bash
npm run check:markers
```

Скрипт анализирует JavaScript-файлы каталога `tests` и завершает процесс с кодом 1, если находит отключающий маркер. Комментарий с таким фрагментом также может быть найден; в тестовых файлах не следует оставлять отключающие примеры.

Удалять сам скрипт, убирать его из `quality` или маскировать маркеры другим синтаксисом вместо завершения тестов нельзя.

## 12. Единый quality gate

Итоговая локальная команда:

```bash
npm run quality
```

Она последовательно выполняет:

1. `format:check`;
2. `lint`;
3. `check:markers`;
4. `test:coverage`.

Используется `&&`: следующий этап не запускается после отказа предыдущего. Код возврата команды должен быть 0.

DB-тест остаётся отдельным:

```bash
npm run test:db
```

Причина разделения — секрет, внешний процесс, изменение состояния и более высокая стоимость. В отчёте фиксируются оба результата. Успешный `quality` без `test:db` не подтверждает PostgreSQL-интеграцию.

## 14. Индивидуальные варианты

Номер сохраняется из предыдущих работ; номер больше восьми приводится по формуле `((номер - 1) % 8) + 1`. Базовые 17 TODO выполняются всеми. Вариант добавляет отдельный тест и контрольную мутацию.

| Вариант | Дополнительный риск | Контрольная мутация, которая должна дать fail |
|---:|---|---|
| 1 | Конфигурация принимает `API_PORT=01` или пробелы вокруг числа. | Ослабить регулярное выражение порта либо применить `parseInt`. |
| 2 | Повторённый `completed` или неизвестный query проходит незамеченным. | Брать только первое значение и не проверять имена query. |
| 3 | Поиск с `%`, `_`, `\` меняет смысл SQL или внедряет фрагмент. | Убрать `escapeLikePattern` перед ILIKE. |
| 4 | PATCH с `completed:false` теряет поле. | Заменить `Object.hasOwn` на truthy-проверку. |
| 5 | Reset не освобождает client после ошибки rollback. | Убрать `release()` из `finally`. |
| 6 | Сломанный JSON превращается в HTML/500 либо пустое тело принимается. | Убрать одно звено `jsonBody`. |
| 7 | SQLSTATE и внутренний detail попадают клиенту. | Отправить `error.message` в 500/503-ответе. |
| 8 | PATCH сообщает успех после удаления между GET и UPDATE. | Не проверять пустой результат `updateTask`. |

Контрольная мутация выполняется только локально. В отчёте указываются изменённая строка, название теста, фактический fail и pass после восстановления. Скриншот без текста теста и объяснения не подтверждает сценарий.

## 16. Типичные ошибки

| Проявление | Причина и исправление |
|---|---|
| `npm test` зелёный при незавершённой работе | TODO не является fail; выполнить `check:markers` и `quality`. |
| Тест всегда проходит | Нет значимого assert либо проверяется константа. |
| Асинхронный отказ появляется после завершения | Promise не await-ится и не возвращается. |
| HTTP-тест иногда получает EADDRINUSE | Используется фиксированный порт; запускать на 0. |
| Процесс тестов не завершается | Не закрыт HTTP-сервер, pool или client. |
| Тесты влияют друг на друга | Общее изменяемое состояние не восстанавливается. |
| Сравнение SQL ломается после форматирования | Сравниваются все пробелы; нормализовать и проверять смысловые фрагменты. |
| Ошибка не совпадает, хотя отказ произошёл | Проверяется любой Error вместо публичного code/details. |
| Покрытие строк высокое, ветви ниже порога | Не проверены отрицательные и альтернативные пути. |
| Coverage 100%, но дефект не найден | Выполнение строки не гарантирует правильный assert. |
| DB-тест «успешно пропущен» | Обязательная проверка скрыта через skip; отсутствие URL должно быть fail. |
| DB-тест повредил рабочие данные | Указана не отдельная учебная база. |
| ESLint и Prettier спорят | Правила форматирования дублируются; формат оставить Prettier, качество кода — ESLint. |
| `format` изменил много файлов | Проверить diff; не коммитить несвязанные изменения автоматически. |
| В репозитории осталась мутация | Перед коммитом проверить diff и повторить quality. |
