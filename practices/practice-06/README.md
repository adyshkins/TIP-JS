# Практическая работа № 6

**Тема: Подключение браузерного приложения к API**

**Дисциплина:** Технологии индустриального программирования<br>
**Трек:** фулстек-разработка на JavaScript<br>
**Форма выполнения:** индивидуальная<br>
**Результат:** браузерный клиент, который получает и изменяет задачи через учебный HTTP API, отображает асинхронные состояния и защищён от устаревших ответов<br>
[К описанию курса](../../README.md) · [ПР5](../practice-05/README.md) · [ПР7](../practice-07/README.md) · [Стартовые файлы](./starter/)

> В ПР5 был разработан модуль чтения данных по HTTP без пользовательского интерфейса. В ПР6 этот модуль расширяется операциями изменения и подключается к DOM-приложению. Сервер предоставлен как учебная инфраструктура: собственный API будет разрабатываться в ПР9–ПР10.

## 1. Цель и результат работы

**Цель работы** — связать интерфейс браузерного приложения с HTTP API и организовать предсказуемое состояние интерфейса во время асинхронных операций.

В ходе работы осваиваются следующие действия:

- отправка `GET`, `POST`, `PATCH` и `DELETE` через `fetch`;
- передача JSON-тела и обработка ответов `200`, `201` и `204`;
- разделение общего HTTP-клиента, предметного API, контроллера и DOM-представления;
- вывод состояний `loading`, `ready`, `empty` и `error`;
- клиентская проверка формы до отправки запроса;
- повторная загрузка данных после изменения на сервере;
- отмена предыдущего запроса и защита от устаревшего ответа;
- безопасный вывод серверных данных как текста;
- модульная, интеграционная и браузерная проверка основных сценариев.

После выполнения в папке `practice-06` работает приложение, в котором:

- категории и задачи поступают из учебного API;
- фильтры превращаются в query-параметры серверного запроса;
- задача создаётся, редактируется, переводится в другой статус и удаляется;
- сервер остаётся единственным источником данных;
- ошибки загрузки и изменения не разрушают уже показанный интерфейс;
- после обновления страницы сохраняются изменения, пока запущен API;
- проходят 70 проверок Node.js и 14 браузерных сценариев;
- README содержит фактические результаты и объяснение принятых решений.

## 2. Подготовка и границы работы

Для выполнения необходимо завершить ПР1–ПР5. Особенно важны следующие результаты предыдущих работ:

- модель задачи и неизменяемые преобразования данных;
- DOM, события, делегирование и формы;

**Предлагаемый формат:** одна аудиторная пара продолжительностью 90 минут с предварительным чтением и самостоятельным завершением.

## 4. Контракт учебного API

### 4.1. Ресурсы и методы

| Метод и путь | Назначение | Успешный ответ |
|---|---|---|
| `GET /api/health` | Проверка доступности | `200`, `{ "data": { "status": "ok" } }` |
| `GET /api/tasks` | Список и фильтры | `200`, `{ data: task[], meta }` |
| `GET /api/tasks/:id` | Одна задача | `200`, `{ data: task }` |
| `GET /api/categories` | Категории | `200`, `{ data: category[], meta }` |
| `POST /api/tasks` | Создание | `201`, `{ data: task }`, заголовок `Location` |
| `PATCH /api/tasks/:id` | Частичное изменение | `200`, `{ data: task }` |
| `DELETE /api/tasks/:id` | Удаление | `204`, пустое тело |
| `POST /api/debug/reset` | Восстановление набора | `200`, `{ data: { reset, total } }` |

Поддерживаемые фильтры `GET /api/tasks`:

- `completed=true` или `completed=false`;
- `priority=low`, `priority=medium` или `priority=high`;
- `categoryId=1`;
- `q=фрагмент` — регистронезависимый поиск по названию.

Фильтры применяются совместно. Неизвестные, неверные и повторяющиеся параметры отклоняются ответом `400`.

### 4.2. Схема данных

```js
{
  id: 35,                 // положительное целое, назначает сервер
  title: "Изучить fetch", // 1–100 символов после trim
  completed: false,       // при создании устанавливает сервер
  priority: "high",      // low | medium | high
  categoryId: 2           // id существующей категории
}
```

Тело создания не содержит `id` и `completed`:

```json
{
  "title": "Изучить fetch",
  "priority": "high",
  "categoryId": 2
}
```

`PATCH` передаёт только изменяемые поля. Для переключения статуса достаточно:

```json
{ "completed": true }
```

Ошибки имеют единый конверт:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Данные задачи не прошли проверку.",
    "details": {
      "title": "Название должно содержать от 1 до 100 символов."
    }
  }
}
```

Клиентская проверка улучшает обратную связь, но не заменяет серверную. Клиент можно обойти, поэтому API повторно проверяет входные данные.

## 5. Теоретические сведения

### 5.1. `fetch` и HTTP-ошибки

Promise от `fetch` отклоняется при сетевой проблеме или отмене, но ответ `404` или `500` сам по себе считается успешно полученным HTTP-ответом. Поэтому статус проверяется явно:

```js
const response = await fetch(url, options);

if (!response.ok) {
  // Преобразование HTTP-ошибки в ApiError
}
```

Сначала обрабатывается неуспешный статус, и только затем проверяется формат успешного ответа. Иначе HTML-страница прокси с кодом `502` может быть ошибочно представлена как проблема `Content-Type`, а важный статус потеряется.

### 5.2. Методы и тела запросов

| Метод | Смысл в этой работе | Тело |
|---|---|---|
| `GET` | Получить состояние | отсутствует |
| `POST` | Создать новый ресурс или выполнить команду reset | JSON для создания; у reset отсутствует |
| `PATCH` | Частично изменить существующий ресурс | JSON с изменяемыми полями |
| `DELETE` | Удалить ресурс | отсутствует |

При наличии JSON-тела добавляется `Content-Type: application/json`, а объект преобразуется через `JSON.stringify`. Заголовок не добавляется автоматически к запросам без тела: его наличие может вызвать лишний CORS preflight и неверно описывает запрос.

### 5.3. Статусы `201` и `204`

`201 Created` сообщает о создании ресурса. Учебный API возвращает созданную задачу и путь к ней в `Location`.

`204 No Content` означает успешный ответ без тела. Вызов `response.json()` для такого ответа завершится ошибкой разбора пустой строки. Поэтому HTTP-клиент возвращает `null` до попытки чтения JSON:

```js
if (response.status === 204) return null;
```

### 5.4. CORS и два локальных порта

Origin определяется схемой, хостом и портом. Адреса `http://127.0.0.1:5505` и `http://127.0.0.1:5506` относятся к разным origin. Перед некоторыми изменяющими запросами браузер может отправить `OPTIONS` и проверить разрешённые методы и заголовки.

Режим `no-cors` здесь не применяется: он не открывает доступ к обычному JSON-ответу. Корректное решение — подходящие CORS-заголовки на API.

### 5.5. Состояние асинхронного интерфейса

Одного массива задач недостаточно. Интерфейсу также требуется знать, идёт ли загрузка и почему список пуст.

| Состояние | Значение | Представление |
|---|---|---|
| `loading` | Ответ ещё не получен | Сообщение о загрузке, `aria-busy="true"` |
| `ready` | Получен непустой список | Карточки и число найденных задач |
| `empty` | Запрос успешен, результатов нет | Явное сообщение без старых карточек |
| `error` | Запрос завершился ошибкой | Понятное сообщение и кнопка повтора |

`empty` не считается ошибкой. Это нормальный результат фильтра или действительно пустого набора.

Изменяющая операция имеет дополнительное состояние ожидания. На это время соответствующие кнопки блокируются, чтобы двойной щелчок не создал два одинаковых запроса.

### 5.6. Сервер как источник истины

После `POST`, `PATCH` или `DELETE` приложение повторно выполняет `GET /tasks` с текущими фильтрами. Такой пессимистический сценарий показывает только подтверждённое сервером состояние:

```text
действие → блокировка → запрос изменения → успешный ответ
        → повторный GET с текущими фильтрами → отрисовка → разблокировка
```

В ПР6 локальная копия не записывается в `localStorage`. Данные принадлежат API, а массив в контроллере является только снимком последнего ответа.

### 5.7. Гонка запросов

Если два запроса запущены подряд, первый может завершиться позднее второго. Без защиты старый результат перезапишет новый фильтр.

Используются два механизма:

1. предыдущий запрос отменяется через `AbortController`;
2. каждому запуску присваивается последовательный номер, и результат применяется только при совпадении с последним номером.

Вторая проверка нужна даже при отмене: тестовый клиент, кэш или другая реализация источника может завершить операцию, не отреагировав на сигнал немедленно.

Отмена при смене фильтра является ожидаемым управлением потоком, поэтому сообщение об ошибке пользователю не выводится.

### 5.8. Доступность и безопасный вывод

Контейнер списка получает `aria-busy`, а сообщения об операции и состоянии размещаются в областях `role="status"` с `aria-live="polite"`. Обновление становится доступно не только визуально.

Название задачи приходит с сервера и считается недоверенным текстом. Оно вставляется через `textContent`, а не через `innerHTML`. Строка вида `<img onerror=...>` отображается буквально и не создаёт HTML-элемент.

### Шаг 1. Выбрать вариант

### Шаг 2. Расширить общий HTTP-клиент

В `src/api-client.js` переносится проверенное решение ПР5. Метод `requestJson` расширяется параметрами `method` и `body`.

Обязательное поведение:

1. допустимы только `GET`, `POST`, `PATCH`, `DELETE`;
2. метод нормализуется в верхний регистр;
3. `GET` с `body` отклоняется до сетевого запроса;
4. к каждому запросу добавляется `Accept: application/json`;
5. при наличии `body` выполняется `JSON.stringify` и добавляется `Content-Type`;
6. сохраняются тайм-аут и внешний `AbortSignal` из ПР5;
7. HTTP-ошибка сохраняет `status`, `code`, `details` и `url`;
8. успешный `204` преобразуется в `null`;
9. у остальных успешных ответов проверяются `Content-Type` и корректность JSON;
10. виды ошибок остаются различимыми: `http`, `network`, `invalid-response`, `timeout`, `aborted`.

После шага запускается:

```bash
npm run check:modules
```

Часть проверок пройдёт, остальные будут указывать на ещё не реализованные модули.

### Шаг 3. Реализовать предметный API задач

В `src/task-api.js` сохраняются функции чтения из ПР5 и добавляются:

```text
getTaskById(id, options)
createTask(draft, options)
updateTask(id, changes, options)
setTaskCompleted(id, completed, options)
deleteTask(id, options)
resetDemoData(options)
```

`options` содержит необязательный `signal`. Предметный модуль не работает с DOM и не формирует пользовательские сообщения. Его задачи:

- выбрать путь и HTTP-метод;
- передать query или body общему клиенту;
- проверить положительный целый `id`;
- проверить форму успешного ответа;
- вернуть удобное значение предметной области.

Для `deleteTask` ожидается строго `null`. Если сервер неожиданно вернул тело, создаётся `ApiError` вида `invalid-response`.

`loadInitialData` загружает список и категории параллельно:

```js
const [taskResult, categories] = await Promise.all([
  getTasks(filters, options),
  getCategories(options),
]);
```

### Шаг 4. Реализовать валидацию формы

`validateTaskDraft(draft, categories)` в `src/form-validation.js` возвращает:

```js
{
  valid: true,
  value: {
    title: "Нормализованное название",
    priority: "medium",
```

Проверяются:

Функция не читает значения из DOM и не изменяет входные объекты.

### Шаг 5. Реализовать карточки задач

В `src/task-view.js` реализуются `createTaskElement` и `renderTaskList`.

Карточка представляет `li.task-card`, содержит `data-task-id` и три кнопки:

```html
<button type="button" data-action="toggle"><span class="action-label">…</span></button>
<button type="button" data-action="edit"><span class="action-label">Изменить</span></button>
<button type="button" data-action="delete"><span class="action-label">Удалить</span></button>
```

Также выводятся:

- локализованный приоритет;
- название категории по `categoryId`.

Список заменяется через `replaceChildren`, чтобы повторная отрисовка не накапливала старые карточки. Для пользовательских строк используется `textContent`.

### Шаг 6. Реализовать контроллер

`createAppController({ api, view })` в `src/app-controller.js` хранит:

- последний список задач;
- категории;
- текущие фильтры;
- `editingId` или `null`;
- активный `AbortController` загрузки;
- номер последней загрузки.

Контроллер возвращает методы:

| Метод | Сценарий |
|---|---|
| `start(filters)` | Первая параллельная загрузка задач и категорий |
| `applyFilters(filters)` | Сохранение фильтров и новый запрос |
| `refresh()` | Повтор текущего запроса |
| `submit(draft)` | Валидация и создание либо редактирование |
| `beginEdit(id)` | Заполнение формы выбранной задачей |
| `cancelEdit()` | Возврат формы в режим создания |
| `toggleTask(id)` | Инверсия `completed` через API |
| `deleteTask(id)` | Удаление через API |
| `resetData()` | Восстановление набора и повторная загрузка |
| `destroy()` | Отмена активной загрузки |

Первая загрузка использует `api.loadInitialData`, последующие — `api.getTasks`. Если начальная загрузка завершилась ошибкой и категории ещё не получены, кнопка повтора снова вызывает `loadInitialData`. При успехе вызываются методы представления, при ошибке — `messageForError` и состояние `error`.

Изменяющие операции выполняются по общей схеме:

```js
view.setMutationPending(true);

try {
  await api.someMutation(...);
  view.notify("Операция выполнена.", "success");
  await loadCurrentTasks();
} catch (error) {
  view.notify(messageForError(error), "error");
} finally {
  view.setMutationPending(false);
}
```

Дублирование этой последовательности выносится во внутреннюю функцию. `app-controller.js` не импортирует `dom-app.js` и не использует глобальный `document`.

### Шаг 7. Проверить точку входа

`src/dom-app.js` и `src/main.js` предоставлены готовыми. После реализации контрактов проверяется:

- адрес API показан в шапке;
- категории появились в форме и фильтре;
- первая загрузка завершилась состоянием `ready`;
- события формы и кнопок вызывают методы контроллера;
- `window.practice06.ready` завершается после начальной загрузки.

Последний объект является только тестовым крючком для `checks.html`; хранить в нём данные приложения не требуется.

## 7. Индивидуальные варианты

Номер сохраняется из ПР2–ПР5. Если вариантов в группе больше восьми, используется циклическое соответствие: `((номер - 1) % 8) + 1`.

| Вариант | Начальный фильтр | Индивидуальный сценарий |
|---:|---|---|
| 1 | `completed=false` | Завершить видимую задачу; после повторного GET она исчезает из выборки. |
| 2 | `completed=true` | Вернуть выполненную задачу в работу; после повторного GET она исчезает из выборки. |
| 3 | `priority=high` | Изменить приоритет видимой задачи на `medium`; карточка исчезает из выборки. |
| 4 | `priority=medium` | Создать задачу среднего приоритета; карточка появляется в текущей выборке. |
| 5 | `categoryId=1` | Перенести задачу в категорию 2; после обновления она исчезает из выборки. |
| 6 | `categoryId=2` | Создать задачу категории «Проект»; карточка появляется в выборке. |
| 7 | `q=провер` | Создать задачу, название которой содержит «Проверить»; поиск находит её без учёта регистра. |
| 8 | `completed=false`, `priority=high`, `categoryId=2` | Создать подходящую задачу, затем завершить её; после второго действия карточка исчезает. |

В отчёте фиксируются начальный запрос, действие, ожидаемое изменение выборки и фактический результат.

## 9. Требования к качеству

### Обязательные требования

- запросы идут через `createApiClient`, прямой `fetch` в контроллере отсутствует;
- все операции задач сосредоточены в `task-api.js`;
- сервер назначает `id` и устанавливает начальный `completed`;
- ответ `204` не разбирается как JSON;
- HTTP-ошибки не маскируются сетевыми;
- фильтры отправляются API, а не применяются только к локальному массиву;
- после мутации выполняется повторный GET с текущими фильтрами;
- старый запрос отменяется, устаревший результат игнорируется;
- отмена не показывается как пользовательская ошибка;
- клиентская валидация не заменяет обработку серверной ошибки;
- названия и категории выводятся через `textContent`;
- список имеет различимые `loading`, `ready`, `empty`, `error`;
- интерактивные элементы остаются доступны с клавиатуры;
- токены, пароли и другие секреты отсутствуют в коде и отчёте.

### Осознанные ограничения

- состояние API хранится только в памяти;
- одновременно работает один общий учебный набор;
- нет аутентификации и разграничения доступа;
- после каждой мутации запрашивается весь отфильтрованный список;
- интерфейс реализован без фреймворка;
- готовый сервер предназначен только для локальной учебной работы.

Эти ограничения не считаются ошибками ПР6. Они будут изменяться на следующих этапах курса.

## 10. Типичные ошибки

| Проявление | Вероятная причина | Проверка |
|---|---|---|
| `Failed to fetch` | API не запущен, неверный порт или CORS | Открыть `/api/health`, проверить Console и Network. |
| 404 показан как `network` | `ApiError` перехвачен общим `catch` | Сначала повторно выбрасывать уже созданный `ApiError`. |
| DELETE падает на JSON | Выполняется `response.json()` при 204 | Вернуть `null` до проверки `Content-Type`. |
| POST получает 415 | Нет `Content-Type: application/json` | Проверить заголовки запроса в Network. |
| POST получает 400 | В body отправлены `id`, `completed` или неверный тип | Сверить тело с контрактом создания. |
| Старые карточки остаются | Использован `append` без очистки | Применить `replaceChildren`. |
| После фильтра виден старый ответ | Нет отмены или проверки номера запроса | Проверить `AbortController` и sequence. |
| После мутации неверная выборка | Список изменён только локально | Повторить GET с сохранёнными фильтрами. |
| Категория не выбирается | `categoryId` остался строкой либо категории ещё не загружены | Нормализовать число и использовать загруженный справочник. |
| Кнопки остаются заблокированными | Нет `finally` | Разблокировать представление в `finally`. |
| `innerHTML` исполняет разметку | Серверный текст вставлен как HTML | Создавать элементы и задавать `textContent`. |
