## 1. Цель и результат работы

**Цель работы** — освоить выполнение асинхронных операций и создать переиспользуемый клиент для получения данных по HTTP.

Для выполнения работы необходимо научиться:

- объяснять порядок синхронного кода, микрозадач Promise и задач таймеров;

- различать успешный HTTP-ответ, HTTP-ошибку, сетевую ошибку и неверный формат ответа;
- формировать URL и query-параметры стандартными средствами;
- проверять `Response.ok`, статус и `Content-Type` до использования данных;
- ограничивать время ожидания и отменять запрос через `AbortSignal`;
- загружать независимые ресурсы параллельно через `Promise.all`;
- отделять общий HTTP-клиент от функций предметной области;
- проверять клиент без реальной сети и вместе с локальным API.

После выполнения должна получиться папка `practice-05`, в которой:

- `main.js` выполняет контрольный сценарий в терминале;
- вариант задаётся только данными в `variant.js`;

## 4. Теоретические сведения

### 4.1. Синхронное и асинхронное выполнение

Синхронные выражения выполняются по очереди в текущем стеке вызовов. Операция ввода-вывода может завершиться позднее, поэтому её результат представляется Promise. Регистрация асинхронной операции не превращает весь JavaScript-код в параллельный.

```js
console.log("до");

const promise = fetch("http://127.0.0.1:5505/api/health");

console.log("после");
```

Сначала выводятся две синхронные строки. Значение `promise` ещё не является телом ответа. Получение `Response`, а затем чтение его тела выполняются асинхронно.

### 4.2. Упрощённая модель цикла событий

Для эксперимента этой работы достаточно различать:

1. текущий синхронный код;
2. микрозадачи продолжений Promise и `await`;
3. следующую задачу, например обработчик таймера.

После завершения текущего синхронного кода среда выполняет доступные микрозадачи, а затем переходит к следующей задаче. Это учебное описание не заменяет полную модель браузера или Node.js: у сред выполнения есть дополнительные фазы и источники задач.

```js
console.log("A");

setTimeout(() => console.log("D"), 0);
Promise.resolve().then(() => console.log("C"));

console.log("B");
```

Нулевая задержка таймера означает минимальную задержку постановки задачи, а не немедленный вызов внутри текущего стека.

### 4.3. Состояния Promise

Promise находится в одном из состояний:

- `pending` — операция ещё не завершена;
- `fulfilled` — получено значение;
- `rejected` — получена причина отказа.

Обработчики `.then()`, `.catch()` и `.finally()` возвращают новый Promise. Ошибка внутри обработчика превращает возвращаемый Promise в отклонённый.

```js
fetch("http://127.0.0.1:5505/api/health")
  .then((response) => response.json())
  .then((payload) => console.log(payload))
  .catch((error) => console.error(error));
```

Создавать `new Promise(...)` вокруг уже существующего Promise без необходимости не требуется.

### 4.4. `async` и `await`

Вызов `async`-функции всегда возвращает Promise. Оператор `await` приостанавливает продолжение только этой функции до урегулирования ожидаемого значения.

```js
async function loadHealth() {
  const response = await fetch("http://127.0.0.1:5505/api/health");
  return response.json();
}

const healthPromise = loadHealth();
console.log(healthPromise instanceof Promise); // true
```

Ошибки ожидаемых Promise обрабатываются через `try`/`catch` либо передаются вызывающему коду. Пустой `catch` скрывает причину сбоя и в работе не используется.

### 4.5. Последовательное и совместное ожидание

Если второй запрос зависит от результата первого, используется последовательность:

```js
const task = await api.getTaskById(25);
const related = await loadRelated(task.categoryId);
```

Если ресурсы независимы, оба запроса можно начать до ожидания:

```js
const tasksPromise = api.getTasks();
const categoriesPromise = api.getCategories();

const [taskResult, categories] = await Promise.all([
  tasksPromise,
  categoriesPromise,
]);
```

`Promise.all` не создаёт параллельность сам по себе: он ожидает уже переданные значения Promise. При отказе одного из них итоговый Promise отклоняется. Остальные операции автоматически не отменяются.

### 4.6. HTTP-запрос и ответ

Для клиентского кода важны:

- URL ресурса;
- HTTP-метод;
- заголовки;
- статус ответа;
- тело ответа.

В ПР5 используется только `GET`. Основные группы статусов:

| Группа | Смысл для этой работы | Примеры |
|---:|---|---|
| `2xx` | запрос обработан успешно | `200`, `204` |
| `4xx` | запрос не соответствует контракту или ресурс не найден | `400`, `404` |
| `5xx` | сервер не смог обработать корректный запрос | `500`, `503` |

Статус является частью протокола. Текст сообщения сервера помогает пользователю, но не заменяет проверку числового статуса и кода API.

### 4.7. Особенность `fetch`

`fetch()` возвращает Promise с объектом `Response`. Ответ со статусом `404` или `503` обычно не отклоняет этот Promise: сервер доступен и отправил HTTP-ответ. Поэтому проверка выполняется явно.

```js
const response = await fetch(url);

if (!response.ok) {
  throw new Error(`HTTP ${response.status}`);
}
```

`response.ok` имеет значение `true` для статусов от `200` до `299`. Сетевой отказ, неверная схема URL или отмена запроса приводят к отклонению Promise.

### 4.8. Заголовок и разбор JSON

До разбора успешного ответа проверяется `Content-Type`:

```js
const contentType = response.headers.get("content-type") ?? "";

if (!contentType.includes("application/json")) {
  throw new Error("Ожидался JSON");
}

const payload = await response.json();
```

`response.json()` также возвращает Promise и может завершиться ошибкой синтаксиса. Тело ответа читается один раз. Для статуса `204 No Content` клиент этой работы возвращает `null`, не пытаясь разобрать отсутствующее тело.

Корректный JSON ещё не подтверждает правильность его структуры. Значение `{"data":"не массив"}` синтаксически корректно, но не соответствует контракту списка задач.

### 4.9. Query-параметры

Фильтры GET-запроса передаются в URL:

```text
/api/tasks?completed=false&priority=high
```

Строки не склеиваются вручную. Для кодирования используется `URLSearchParams`, доступный через объект `URL`.

```js
const url = new URL("http://127.0.0.1:5505/api/tasks");
url.searchParams.set("q", "API & ошибки");
```

Значения `false` и `0` нельзя удалять проверкой `if (value)`: они могут быть содержательными. В контракте `buildUrl` пропускаются только `undefined`, `null` и пустая строка.

### 4.10. Контракт API

Успешная коллекция:

```json
{
  "data": [
    {
      "id": 4,
      "title": "Подготовить модель задач",
      "completed": false,
      "priority": "high",
      "categoryId": 2
    }
  ],
  "meta": {
    "total": 1,
    "filters": {
      "completed": false,
      "priority": "high",
      "categoryId": 2,
      "q": ""
    }
  }
}
```

Ошибка:

```json
{
  "error": {
    "code": "TASK_NOT_FOUND",
    "message": "Задача с id 999 не найдена.",
    "details": {
      "id": 999
    }
  }
}
```

Клиент использует стабильный машинный `code`, а сообщение сохраняет для вывода. Проверка строится по контракту, а не по совпадению полного текста сообщения.

### 4.11. Ограничение времени и отмена

`fetch` не задаёт прикладной тайм-аут автоматически. Для ограничения времени используется `AbortSignal.timeout()`; для явной отмены — `AbortController`.

```js
const controller = new AbortController();

const pending = fetch(url, { signal: controller.signal });
controller.abort();

await pending;
```

Если одновременно поддерживаются внешний сигнал и тайм-аут, сигналы можно объединить через `AbortSignal.any()`. Клиент различает:

- `timeout` — истекло заданное время;
- `aborted` — вызывающий код отменил операцию.

### 4.12. Классификация ошибок клиента

Вместо анализа случайных текстов используется `ApiError` с полем `kind`.

| `kind` | Причина | Значимые поля |
|---|---|---|
| `http` | сервер вернул статус вне `2xx` | `status`, `code`, `details`, `url` |
| `network` | ответ от сервера не получен | `cause`, `url` |
| `invalid-response` | неверный `Content-Type`, JSON или схема | `cause`, `url` |
| `timeout` | превышено время ожидания | `cause`, `url` |
| `aborted` | запрос отменён внешним сигналом | `cause`, `url` |

HTTP-ошибка не должна повторно превращаться в сетевую из-за слишком широкого `catch`. Удобно отдельно перехватывать вызов `fetch`, а обработку полученного `Response` выполнять после него.

### 4.13. Разделение общего и предметного клиента

`api-client.js` не знает, что такое задача. Он отвечает за транспорт:

```text
путь + параметры
        ↓
       fetch
        ↓
статус и Content-Type
        ↓
     JSON / ApiError
```

`task-api.js` знает маршруты и схему:

```text
getTasks(filters) ───────→ /tasks
getTaskById(id) ─────────→ /tasks/:id
getCategories() ─────────→ /categories
loadInitialData(filters) → Promise.all
```

Такой модуль позже можно вызвать из DOM-интерфейса или React-компонента без копирования кода `fetch`.

### 4.14. Подмена `fetch` в модульной проверке

В `createApiClient` функция `fetchFn` передаётся аргументом:

```js
const client = createApiClient({
  baseUrl,
  fetchFn: fakeFetch,
});
```

Проверка может вернуть подготовленный `Response`, зафиксировать URL и смоделировать ошибку без запуска сети. Интеграционный набор отдельно подтверждает совместимость с настоящим локальным API.

### 4.15. CORS и граница ПР5

CORS применяется браузером к запросам между разными origin. Сервер заготовки отправляет разрешающие заголовки для будущей ПР6. Запросы Node.js из этой работы не являются проверкой браузерной политики CORS.

Режим `no-cors` не используется как способ исправления CORS: в браузере он ограничивает запрос и делает ответ непрозрачным для JavaScript. Настройка разрешённых origin относится к серверу.

## 5. Учебный API и контракты модулей

### 5.1. Модель задачи и категории

Задача:

```js
{
  id: 4,
  title: "Подготовить модель задач",
  completed: false,
  priority: "high",
  categoryId: 2
}
```

Правила:

- `id` — положительное безопасное целое число;
- `title` — непустая строка длиной до 100 после `trim`;
- `completed` — логическое значение;
- `priority` — `low`, `medium` или `high`;
- `categoryId` — положительное безопасное целое число.

Категория:

```js
{
  id: 2,
  name: "Проект"
}
```

Коллекция не должна содержать повторяющиеся `id`. Для ответа коллекции `meta.total` равен длине `data`.

### 5.2. Рабочие маршруты

| Метод и путь | Результат |
|---|---|
| `GET /api/health` | состояние учебного API |
| `GET /api/tasks` | все задачи или отфильтрованная коллекция |
| `GET /api/tasks/:id` | одна задача либо ошибка |
| `GET /api/categories` | все категории |
| `GET /api/categories/:id` | одна категория либо ошибка |

Фильтры `/api/tasks`:

| Параметр | Допустимые значения | Пример |
|---|---|---|
| `completed` | `true`, `false` | `?completed=false` |
| `priority` | `low`, `medium`, `high` | `?priority=high` |
| `categoryId` | положительное целое | `?categoryId=2` |
| `q` | строка до 100 символов | `?q=провер` |

Несколько фильтров применяются одновременно. Повторение одного параметра, неизвестный параметр и неверный тип дают `400 INVALID_QUERY`.

### 5.3. Отладочные маршруты

Они нужны только для воспроизводимых ошибочных сценариев:

| Путь | Назначение |
|---|---|
| `/api/debug/error` | JSON-ошибка `503 SERVICE_UNAVAILABLE` |
| `/api/debug/invalid-json` | успешный статус с повреждённым JSON |
| `/api/debug/text` | успешный текст вместо JSON |
| `/api/debug/delay?ms=150` | ответ после заданной задержки от 0 до 5000 мс |

В прикладной код приложения эти маршруты не включаются.

### 5.4. `buildUrl`

Экспортируемая функция:

```js
buildUrl(baseUrl, path, query = {}) -> string
```

Контракт:

- `baseUrl` — абсолютный `http`- или `https`-адрес без query и hash;
- `path` — непустой относительный путь;
- `query` — обычный объект;
- начальные и конечные `/` не создают двойной разделитель;
- значения кодируются `URLSearchParams`;
- `undefined`, `null` и `""` пропускаются;
- `false` и `0` сохраняются;
- входной объект не изменяется.

### 5.5. `createApiClient`

Фабрика:

```js
const client = createApiClient({
  baseUrl,
  fetchFn: globalThis.fetch,
  timeoutMs: 2000,
});
```

Возвращаемый метод:

```js
client.requestJson(path, {
  query,
  signal,
  timeoutMs,
});
```

`requestJson`:

1. формирует URL через `buildUrl`;
2. выполняет `GET`;
3. передаёт `Accept: application/json`;
4. объединяет внешний сигнал с тайм-аутом;
5. преобразует отказ `fetch` в `network`, `timeout` или `aborted`;
6. убеждается, что получен `Response`;
7. при HTTP-ошибке создаёт `ApiError` вида `http`;
8. для успешного `204` возвращает `null`;
9. проверяет JSON `Content-Type`;
10. возвращает разобранное значение либо ошибку `invalid-response`.

### 5.6. `createTaskApi`

Фабрика получает готовый общий клиент:

```js
const api = createTaskApi(client);
```

Контракт методов:

| Метод | Результат |
|---|---|
| `getTasks(filters = {})` | `Promise<{ tasks, meta }>` |
| `getTaskById(id)` | `Promise<task>` |
| `getCategories()` | `Promise<category[]>` |
| `loadInitialData(filters = {})` | `Promise<{ tasks, categories, meta }>` |

До запроса проверяются только допустимые фильтры. После запроса проверяется форма полученных данных. Ошибка схемы представляется как `ApiError` с `kind: "invalid-response"`.

`loadInitialData` начинает запрос задач и запрос категорий до ожидания общего результата.

## 12. Частые ошибки

### Ошибка 1. Данные используются без `await`

```js
const tasks = api.getTasks();
console.log(tasks.length);
```

В переменной находится Promise. Необходимо дождаться результата в `async`-функции.

### Ошибка 2. `fetch` считается отклонённым для `404`

```js
const response = await fetch(url);
return response.json();
```

Перед чтением успешного результата проверяется `response.ok`.

### Ошибка 3. Весь код помещён в один `try`

HTTP-ошибка, созданная после `fetch`, попадает в общий `catch` и ошибочно получает `kind: "network"`. Перехват сетевого этапа и обработка `Response` разделяются.

### Ошибка 4. Параметры склеиваются вручную

```js
const url = baseUrl + "?q=" + query;
```

Специальные символы и несколько параметров приводят к неверному адресу. Используются `URL` и `URLSearchParams`.

### Ошибка 5. Теряется `false`

```js
if (value) url.searchParams.set(name, value);
```

При таком условии `completed: false` исчезает. Пропускаются только значения, перечисленные в контракте.

### Ошибка 6. Разбирается любое успешное тело

`200` с HTML или повреждённым JSON не является корректным результатом предметного API. Проверяются `Content-Type`, синтаксис JSON и схема.

### Ошибка 7. Независимые запросы выполняются последовательно

```js
const tasks = await api.getTasks();
const categories = await api.getCategories();
```

Для независимых ресурсов Promise создаются до общего ожидания.

### Ошибка 8. `Promise.all` понимается как запуск функций

В `Promise.all([first, second])` передаются уже полученные Promise. Если передать сами функции без вызова, запросы не начнутся.

### Ошибка 9. Тайм-аут реализован только через `Promise.race`

Гонка может прекратить ожидание, но не обязательно отменяет сетевую операцию. В работе сигнал передаётся самому `fetch`.

### Ошибка 10. Используется `mode: "no-cors"`

Этот режим не открывает доступ к запрещённому ответу. Для будущего браузерного клиента CORS настраивается сервером.

### Ошибка 11. Меняется готовый сервер под ошибочный клиент

Контракт сервера уже проверяется отдельным набором. В обязательной части исправляются `src/api-client.js` и `src/task-api.js`.

### Ошибка 12. Проверки подменяются константами

Возврат массива ожидаемых id без выполнения запроса проходит только отдельный узкий случай и нарушает общий контракт. Проверяются другие фильтры, ошибки и реальные ответы.
