## 3. Что считается релизом

Релиз — не архив с `node_modules` и не снимок работающей машины. Для этой работы релиз задаётся четырьмя видами информации:

| Часть | Где зафиксирована | Что подтверждает |
| --- | --- | --- |
| Исходный код | Git commit | точное содержимое приложения; |
| Зависимости и runtime | `package-lock.json`, `engines`, Dockerfile | воспроизводимое окружение; |
| Конфигурационный контракт | `.env.example`, README | необходимые внешние параметры; |
| Доказательства | тесты, CI, smoke, сценарий демонстрации | проверенное поведение версии. |

Рабочее дерево перед выпуском должно быть чистым. Версия в `package.json`, `RELEASE_VERSION`, CHANGELOG и Git-тег должна обозначать один и тот же выпуск.

Для первой итоговой версии используется `1.0.0`. Увеличение компонентов версии трактуется следующим образом:

- patch — совместимое исправление дефекта;
- minor — новая совместимая возможность;
- major — несовместимое изменение контракта.

В учебной работе применяется смысловая модель версий, но публикация пакета в npm не выполняется.

## 5. Конфигурация среды

Расширить `readConfig(env)` без прямого изменения `process.env`. Результат должен содержать:

| Переменная | Поле | Значение по умолчанию | Ограничение |
| --- | --- | --- | --- |
| `API_HOST` | `host` | `127.0.0.1` | непустая строка без пробелов, не длиннее 255; |
| `API_PORT` | `port` | `5505` | целое 1024–65535; |
| `DATABASE_URL` | `connectionString` | нет | обязательная непустая строка; |
| `ENABLE_DEBUG_RESET` | `enableDebugReset` | `false` | только `true` или `false`; |
| `NODE_ENV` | `environment` | `development` | `development`, `test` или `production`; |
| `LOG_LEVEL` | `logLevel` | `info` | `debug`, `info`, `warn` или `error`; |
| `RELEASE_VERSION` | `releaseVersion` | `0.0.0-local` | 1–64 символа: буквы, цифры, `.`, `_`, `-`. |

При `NODE_ENV=production` значение `ENABLE_DEBUG_RESET=true` должно приводить к отказу запуска. Отключение опасного маршрута только документацией недостаточно: ограничение закрепляется кодом и тестом.

Разница между конфигурацией и секретом:

- имя порта и уровень логов можно документировать;
- пароль и строку подключения нельзя публиковать;
- `.env.example` описывает имена и форму значений, но не содержит рабочие секреты;
- CI использует отдельный одноразовый пароль только для изолированного service container.

## 6. Проверка состояния процесса

Реализовать `createHealthRouter({ store, releaseVersion })` и подключить router в `createApp` по пути `/health` до `/api`.

### 6.1. Liveness

`GET /health/live` показывает, что процесс принимает HTTP-запросы:

```json
{
  "status": "ok"
}
```

Endpoint отвечает `200` и **не обращается к PostgreSQL**. Отказ базы не означает, что процесс завис и его обязательно требуется немедленно перезапустить.

### 6.2. Readiness

`GET /health/ready` показывает, можно ли направлять прикладные запросы:

```json
{
  "status": "ready",
  "version": "1.0.0"
}
```

Перед успешным ответом выполняется `store.ping()`. При отказе базы возвращаются статус `503` и безопасное тело:

```json
{
  "status": "not_ready",
  "version": "1.0.0"
}
```

В ответ не попадают SQLSTATE, адрес сервера, имя пользователя, пароль, stack trace или текст драйвера.

Завершить три теста `tests/integration/health.test.js`. В liveness-тесте fake store должен выбрасывать ошибку при любом обращении: так подтверждается отсутствие скрытой зависимости от базы.

## 7. Структурированные логи и request id

Реализовать в `src/logger.js` две функции:

```js
createLogger({ level, output, clock })
requestLogger({ logger, createRequestId, clock })
```

Зависимости `output`, `clock` и `createRequestId` передаются явно, чтобы тесты не меняли глобальные часы и `stdout`.

Каждая строка production-лога представляет один JSON-объект. Минимальные поля события:

```json
{
  "timestamp": "...",
  "level": "info",
  "event": "http_request",
  "requestId": "...",
  "method": "GET",
  "path": "/api/tasks",
  "status": 200,
  "durationMs": 4.2
}
```

Правила:

- уровни упорядочены как `debug < info < warn < error`;
- события ниже настроенного уровня не записываются;
- одна запись завершается одним переводом строки;
- в поле `path` не сохраняется query string с пользовательскими данными;
- ключи `password`, `authorization`, `cookie`, `connectionString` скрываются как `[REDACTED]` независимо от регистра;
- `X-Request-Id` создаётся сервером, возвращается клиенту и присутствует в итоговой записи;
- завершение запроса фиксируется по событию ответа, поэтому доступны реальный статус и длительность;
- тело запроса и полный объект ошибки по умолчанию не логируются.

Для генерации id подходит `randomUUID()` из `node:crypto`. Для измерения интервала — монотонные часы, например `performance.now()`. Временная метка и длительность имеют разные задачи и не должны вычисляться одним способом.

Подключить middleware до маршрутов. Завершить четыре теста `tests/unit/logger.test.js`. Проверка скрытия выполняется не только для верхнего уровня, но и для вложенных объектов.

## 8. Корректное завершение

Контейнерная платформа и терминал передают процессу сигналы. После установки собственного обработчика SIGINT или SIGTERM Node.js не выполняет стандартный выход автоматически, поэтому завершение должно быть явным.

Реализовать `createShutdown({ server, pool, logger, timeoutMs })`. Функция возвращает обработчик `shutdown(signal)` со следующей последовательностью:

1. повторный вызов возвращает уже созданный Promise;
2. сервер прекращает принимать новые подключения;
3. существующие HTTP-запросы получают возможность завершиться;
4. pool PostgreSQL закрывается;
5. записывается итоговое событие;
6. вся операция ограничивается `timeoutMs`, по умолчанию 10 секундами.

Модуль жизненного цикла не вызывает `process.exit()` внутри тестируемой функции. Точка входа `src/server.js` назначает `process.exitCode` после успешного или аварийного результата.

Обновить `src/server.js`:

- создать logger после чтения config;
- передать logger и release version в приложение;
- слушать `config.host` и `config.port`;
- зарегистрировать однократные обработчики SIGINT и SIGTERM;
- не выводить `DATABASE_URL` и пароль;
- заменить свободный текст запуска и ошибок структурированными событиями.

Завершить три теста `tests/unit/lifecycle.test.js`. Для проверки таймаута передать короткое контролируемое значение; ожидание 10 секунд в unit-тесте недопустимо.

## 9. Production-образ

Starter содержит двухэтапный Dockerfile:

- зависимости устанавливаются через `npm ci --omit=dev`;
- runtime-слой содержит только production-зависимости, `package.json` и `src`;
- процесс выполняется непривилегированным пользователем `node`;
- `.env`, тесты, документы, Git и локальные зависимости исключены из build context;
- healthcheck обращается к liveness endpoint.

Проверить содержимое и собрать образ:

```bash
docker build --check .
docker build --tag tip-pr14:1.0.0 .
docker image inspect tip-pr14:1.0.0
```

Не передавать секрет через `ARG` или `ENV` Dockerfile: значение может попасть в метаданные и слои образа. `DATABASE_URL` задаётся только при запуске контейнера.

Образ не содержит PostgreSQL. Один контейнер выполняет одну роль; API и база описываются отдельными services в Compose.

## 10. Запуск через Docker Compose

После заполнения `.env` проверить итоговую конфигурацию:

```bash
docker compose config
```

Команда показывает развёрнутые значения, включая пароль. Её полный вывод нельзя публиковать в отчёте или CI-логе.

Запустить проект:

```bash
docker compose up --build -d
docker compose ps
docker compose logs --tail=50 api
npm run smoke
```

`depends_on` ожидает healthcheck PostgreSQL, но готовность API всё равно подтверждается отдельным readiness endpoint. Это разные уровни проверки.

Проверить постоянство данных:

1. создать запись через API;
2. выполнить `docker compose restart api`;
3. получить созданную запись повторно;
4. убедиться, что id и значения сохранились.

Обычная остановка сохраняет named volume:

```bash
docker compose down
```

Команда ниже удаляет данные базы и применяется только к осознанно выбранному учебному проекту:

```bash
docker compose down -v
```

Перед её выполнением проверяется имя Compose-проекта и отсутствие нужных данных. Удаление volume не является обычным способом остановки.

## 11. Smoke-проверка

`tools/smoke.mjs` проверяет уже запущенный экземпляр по `SMOKE_BASE_URL`:

- liveness возвращает `200` и `status: ok`;
- readiness возвращает `200`, `status: ready` и строковую версию;
- чтение задач возвращает `200` и массив `data`.

По умолчанию используется `http://127.0.0.1:5505`.

```bash
npm run smoke
```

Smoke-тест короткий и не заменяет unit, integration или DB-тесты. Его задача — обнаружить ошибки сборки, переменных, сетевого связывания и запуска компонентов.

После базового сценария выполнить отрицательную ручную проверку:

1. остановить только `db`;
2. убедиться, что `/health/live` остаётся `200`;
3. убедиться, что `/health/ready` становится `503`;
4. запустить `db` и дождаться восстановления readiness.

## 12. Непрерывная интеграция

`.github/workflows/quality.yml` запускается для push и pull request. Job:

1. получает код;
2. поднимает изолированный PostgreSQL service с healthcheck;
3. устанавливает Node.js 24 и кэш npm;
4. выполняет `npm ci`;
5. запускает `npm run release:check`;
6. собирает production-образ.

Учебный пароль в workflow относится только к одноразовой базе runner и не используется вне job. Реальный пароль из `.env` в GitHub Actions не переносится.

После push открыть запуск Actions и проверить каждый step. Красный job не исправляется отключением проверки, `continue-on-error`, `test.skip` или снижением порогов покрытия.

Локальный и CI gate используют одну и ту же npm-команду. Отдельная «облегчённая» CI-команда создаёт риск расхождения результатов.

| 9 | Добавить healthcheck API в Compose, чтобы `docker compose ps` показывал его состояние. |
| 10 | Запустить API-контейнер с read-only filesystem и явно выделенным временным каталогом. |
| 11 | Добавить безопасные скрипты backup и restore для учебной базы с проверкой аргументов. |
| 12 | Добавить в CI запуск контейнера API и smoke-проверку собранного образа. |
| 13 | Передавать короткий commit SHA как build metadata и возвращать его в readiness. |
| 14 | Поддержать человекочитаемый лог в development и JSON только в production. |

Расширение не может ослаблять обязательные проверки, раскрывать секреты или менять публичный контракт без документирования.

## 15. Репетиция итоговой демонстрации

Рекомендуемый основной сценарий рассчитан на 8–10 минут:

| Время | Показ | Доказательство |
| ---: | --- | --- |
| 0:00–1:00 | версия, commit, tag и архитектура | чистое дерево и схема компонентов; |
| 1:00–2:00 | воспроизводимый запуск | `docker compose up`, `ps`, readiness; |
| 2:00–4:00 | основной пользовательский сценарий | создание, чтение, изменение, фильтрация; |
| 4:00–5:00 | валидация и безопасная ошибка | неверный запрос без утечки деталей; |
| 5:00–6:00 | постоянство | restart API и повторное чтение; |
| 6:00–7:00 | наблюдаемость | request id и JSON-запись; |
| 7:00–8:00 | quality и CI | локальный gate и зелёный workflow; |
| 8:00–9:00 | вариант и ограничение | тест, реализация, оставшийся риск. |

Во время показа не выполняются впервые команды, способные удалить volume, изменить историю Git или раскрыть `.env`. Длинная сборка выполняется заранее; основной сценарий при этом остаётся воспроизводимым командами из README.

Запасной сценарий не заменяет живой показ, но позволяет продолжить объяснение при временной проблеме сети или реестра образов.

## 16. Порядок итоговой проверки

### 16.1. Локальный gate

```bash
npm ci
npm run quality
```

Ожидается не менее 56 pass, 0 fail, 0 todo, 0 skip и сохранение порогов ПР13:

- строки — не менее 85%;
- функции — не менее 85%;
- ветви — не менее 75%.

### 16.2. Проверка с PostgreSQL

```bash
npm run db:prepare
npm run test:db
npm run release:files
```

Для DB-теста используется отдельная учебная база, поскольку сценарий сбрасывает и изменяет данные.

### 16.3. Контейнерная проверка

```bash
docker compose up --build -d
docker compose ps
npm run smoke
docker compose down
```

### 16.4. Git

```bash
git status --short
git diff --check
git log -1 --oneline
```

После успешной проверки создать релизный коммит, затем аннотированный тег:

```bash
git add .
git commit -m "Prepare final release"
git tag -a v1.0.0 -m "Final course release 1.0.0"
git push origin main
git push origin v1.0.0
```

Тег создаётся только на проверенном коммите. Если после тега понадобилось исправление, существующий опубликованный тег не перемещается: выпускается следующая версия.

## 17. Критерии приёмки

Работа принимается при одновременном выполнении условий:

- репозиторий клонируется и зависимости устанавливаются через `npm ci`;
- секреты и локальные артефакты отсутствуют в отслеживаемых файлах;
- все 14 релизных TODO заменены содержательными тестами;
- добавлен и проходит тест индивидуального варианта;
- `npm run quality` проходит с установленными порогами;
- DB-тест проходит на отдельной PostgreSQL;
- liveness не зависит от БД, readiness корректно отражает её отказ;
- логи коррелируются request id и скрывают чувствительные значения;
- SIGINT и SIGTERM закрывают сервер и pool в ограниченное время;
- образ выполняется не от root и не содержит devDependencies или `.env`;
- Compose запускает оба сервиса, данные переживают restart API;
- smoke проходит на контейнерном экземпляре;
- GitHub Actions зелёный и собирает образ;
- релизные документы заполнены и не противоречат командам проекта;
- commit, версия и тег согласованы;
- демонстрация укладывается в подготовленный сценарий, а решения объясняются без чтения кода вслух.

Скриншот сам по себе не подтверждает воспроизводимость. Основные доказательства — исходники, команды, тесты, история CI и наблюдаемое поведение.

## 19. Требования к отчёту

Заполнить `README.md` внутри проекта и приложить ссылки на:

- релизный commit;
- аннотированный tag;
- успешный workflow;
- при наличии — pull request с итоговым изменением.

В отчёте не размещаются пароли, токены, полный `DATABASE_URL`, cookie, дампы с персональными данными и полный `docker compose config`.

Для результатов команд достаточно краткого значимого фрагмента: число тестов, покрытие, состояние services, ответ health и идентификатор commit. Большие журналы заменяются ссылкой на запуск CI или приложением без секретов.
