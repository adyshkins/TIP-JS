## 1. Цель и результат работы

**Цель работы** — связать данные и прикладные функции с браузерным интерфейсом, освоить создание DOM-элементов, обработку событий и обновление представления после изменения состояния.

Для выполнения работы необходимо научиться:

- находить, создавать и обновлять элементы страницы средствами DOM;
- выводить значения как текст, не превращая название задачи в HTML-разметку;
- обрабатывать нажатия через `addEventListener`, всплытие и делегирование;
- различать `event.target`, `event.currentTarget`, идентификатор задачи и индекс массива;
- хранить полный список отдельно от выбранного фильтра и отображаемой выборки;
- проверять интерфейс на обычных, пустых и ошибочных состояниях.

**Итоговое приложение:** список задач с приоритетом и статусом, кнопками изменения статуса и удаления, тремя фильтрами, общей сводкой, счётчиком показанных записей и понятными сообщениями. Для общего и индивидуального наборов используется один и тот же код.

### 3.5. Почему не подходит двойной щелчок по HTML

В `index.html` подключён модуль:

```html
<script type="module" src="./src/main.js"></script>
```

Для модульных примеров необходим запуск через HTTP-сервер: открытие как `file://` может приводить к ограничениям загрузки модулей. В браузере тип скрипта задаётся атрибутом `type="module"`; поле `"type": "module"` в `package.json` относится к выполнению файлов в Node.js. Подробнее: [браузерные модули][js-modules] и [пакеты Node.js][node-packages].

**Начальное состояние заготовки:** страница открывается, но появляется сообщение «Ошибка запуска: Не реализовано: renderApp». Это обозначение отсутствующей реализации. Исчезновение сообщения само по себе не означает готовность работы — необходимо выполнить поведение и проверки.

## 4. Теоретические сведения

### 4.1. DOM: HTML как дерево объектов

DOM представляет документ через объекты, с которыми можно работать из JavaScript. Элемент HTML, его текст и его атрибуты — не одно и то же. Например, внутри `<button><span>Открыть</span></button>` находятся кнопка, вложенный элемент `span` и текстовый узел. Общие сведения: [введение в DOM][dom-intro].

Для выбора элемента используется CSS-селектор:

```js
const title = document.querySelector("#page-title");
const buttons = document.querySelectorAll(".toolbar button");
```

`querySelector` возвращает первый подходящий элемент или `null`. `querySelectorAll` возвращает коллекцию `NodeList`, в том числе пустую. Это не результат чтения массива задач — поиск выполняется в документе. Источники: [querySelector][dom-query], [querySelectorAll][dom-query-all].

```js
const missing = document.querySelector("#missing-element");
console.log(missing); // null

// Без проверки следующая строка вызовет ошибку:
// missing.textContent = "Текст";
```

Коллекция, полученная через `querySelectorAll`, статическая: добавление новых узлов не увеличивает ранее сохранённую коллекцию. Для нового снимка необходим новый запрос. Это поведение не следует переносить на любые коллекции DOM: разные API возвращают разные виды коллекций. Источник: [querySelectorAll][dom-query-all].

### 4.2. Создание и размещение элементов

Создание элемента и добавление в документ — разные действия:

```js
const note = document.createElement("p");
note.classList.add("hint");
note.textContent = "Проверьте данные перед продолжением";

const container = document.querySelector("#notes");
container.append(note);
```

`createElement` создаёт элемент заданного типа. `append` добавляет узлы в конец выбранного контейнера. Для замены его содержимого можно использовать `replaceChildren`; вызов без аргументов очищает дочерние узлы. Источники: [createElement][dom-create], [append][dom-append], [replaceChildren][dom-replace].

```js
container.replaceChildren(note);
container.replaceChildren();
```

Во втором случае сам `container` остаётся в документе. Для ПР3 это важно: обработчик будет назначен контейнеру списка и сохранится при замене карточек.

### 4.3. Текст не равен HTML

Для вывода названия задачи используется `textContent`:

```js
const value = "<strong>Проверить пример</strong>";
const label = document.createElement("span");
label.textContent = value;
```

На странице отображается строка с угловыми скобками; элемент `strong` из этой строки не создаётся. В отличие от этого, `innerHTML` разбирает значение как HTML. Для пользовательских названий в этой работе HTML-интерпретация не нужна. Источник: [textContent][dom-text].

Использование `textContent` здесь относится именно к текстовому содержимому. Оно не является универсальным способом проверки URL, разрешений или любых других данных приложения.

**Ограничение задания:** `innerHTML`, `outerHTML` и `insertAdjacentHTML` не используются для построения карточек. Структура создаётся через DOM-методы, а названия, статусы и сообщения назначаются как текст.

### 4.4. Классы и видимость

Состояние оформления удобно выражать классами:

```js
card.classList.add("selected");
card.classList.remove("selected");
card.classList.toggle("selected", isSelected);
```

В варианте с двумя аргументами `toggle` приводит наличие класса к заданному логическому условию. Источник: [classList][dom-classes].

Для сообщения о пустом списке используется свойство `hidden`:

```js
message.hidden = true;
message.hidden = false;
```

В шаблоне есть CSS-правило для `[hidden]`, поэтому собственное оформление не должно отменять скрытие. Подробнее: [hidden][dom-hidden].

Свойству передаётся логическое значение. Не нужно записывать строку `"false"` в атрибут `hidden` в расчёте на показ элемента: наличие HTML-атрибута и логическое значение JavaScript — разные механизмы. Источник: [HTML hidden][html-hidden].

### 4.5. Событие и обработчик

Обработчик — функция, вызываемая при событии:

```js
const button = document.querySelector("#details-button");

function handleDetailsClick(event) {
  console.log("Обработчик вызван", event.type);
}

button.addEventListener("click", handleDetailsClick);
```

В `addEventListener` передаётся функция, а не результат её немедленного вызова. Запись `handleDetailsClick()` на месте второго аргумента имеет другой смысл. Источник: [addEventListener][event-listener].

При повторном создании анонимных функций получаются разные обработчики. Поэтому назначение новых анонимных обработчиков внутри каждой отрисовки может привести к накоплению реакций. Повторное добавление той же самой функции с теми же существенными параметрами не нужно считать новым обработчиком автоматически. Источник: [addEventListener][event-listener].

В этой работе подписки вынесены из `renderApp`: контейнеры получают обработчики один раз.

### 4.6. `target`, `currentTarget` и всплытие

Пусть обработчик находится на контейнере, а нажатие произошло по `span` внутри кнопки. Тогда `event.target` указывает на исходную цель события, а `event.currentTarget` — на объект, чей обработчик сейчас выполняется. После обработки на целевом элементе событие `click` может пройти по цепочке предков — это всплытие. Источники: [currentTarget][event-current], [распространение событий][event-bubbling].

```text
ul — на нём назначен обработчик
└── li
    └── button
        └── span — нажатие произошло здесь
```

В таком случае проверка только `event.target.dataset.action` ненадёжна: атрибут может находиться у кнопки, а не у `span`.

### 4.7. Делегирование событий и `closest`

Делегирование позволяет обрабатывать действия множества дочерних элементов одним обработчиком на их общем контейнере. В данном задании это удобно ещё и потому, что карточки пересоздаются при отображении. Механизм основан на распространении события; подробнее — [MDN][event-bubbling].

Пример для отдельной панели, не готовое решение обработчика задач:

```js
const toolbar = document.querySelector("#toolbar");

toolbar.addEventListener("click", (event) => {
  if (!(event.target instanceof Element)) return;

  const button = event.target.closest("button[data-command]");
  if (!button || !toolbar.contains(button)) return;

  console.log("Команда:", button.dataset.command);
});
```

`closest` проверяет сам элемент, затем его предков и возвращает ближайшее совпадение или `null`. Проверка `contains` ограничивает результат нужным контейнером. Источники: [closest][dom-closest], [contains][dom-contains].

В ПР3 не нужно назначать отдельные обработчики каждой карточке. Также не требуется `stopPropagation`: обычное всплытие необходимо для выбранного способа обработки.

### 4.8. `data-*` и идентификатор задачи

Атрибуты `data-*` связывают элемент с небольшими служебными значениями:

```html
<li data-task-id="23">
  <button type="button" data-action="delete">Удалить</button>
</li>
```

```js
const card = document.querySelector("li[data-task-id]");

console.log(card.dataset.taskId);        // "23"
console.log(typeof card.dataset.taskId); // "string"

const id = Number(card.dataset.taskId);
```

В `dataset` значения представлены строками, а дефисное имя `data-task-id` становится свойством `taskId`. Источник: [dataset][dom-dataset].

В модель ПР2 передаётся число. До вызова прикладной функции необходимо проверить `Number.isSafeInteger(id)` и `id > 0`. Строка `"4abc"` не должна превращаться в идентификатор `4`: для этой границы используется `Number`, а не частичный разбор через `parseInt`. См. [Number][js-number] и [isSafeInteger][js-safe-integer].

Атрибут помогает выбрать запись, но не превращается в источник её статуса. Текущий `completed` читается из массива через `findTaskById`.

### 4.9. Данные, выборка и отображение

В приложении вводятся две переменные:

```js
let currentTasks = initialTasks.map((task) => ({ ...task }));
let currentFilter = "all";
```

Это выбранная для работы организация состояния. `currentTasks` хранит все актуальные задачи, `currentFilter` — режим отображения. Видимый список рассчитывается отдельно.

```text
Текущий полный массив + выбранный фильтр
                 ↓
           Видимая выборка
                 ↓
              Карточки
```

**Фильтрация не удаляет данные.** Присваивание отфильтрованной выборки в `currentTasks` нарушает контракт приложения: после этого кнопка «Все» не сможет вернуть скрытые записи.

Для операций изменения используется другая последовательность:

```text
Событие → действие и id → функция ПР2 → проверка ok
                                      ↓ успех
                             новое currentTasks
                                      ↓
                                  renderApp()
```

Простое удаление `<li>` через DOM не считается удалением задачи: после повторной отрисовки запись появится снова, если массив не изменён.

### 4.10. Кнопки и доступность

Действия выполняются через настоящие элементы `<button type="button">`, а не кликабельные `div`. Для переключаемой кнопки используется `aria-pressed`, а для фильтров — согласованное состояние активной кнопки. Название переключателя «Выполнена» сохраняется; меняется признак нажатия, а не смысл подписи. Источники: [button][html-button], [aria-pressed][aria-pressed].

Кроме цвета у выполненной задачи остаётся текстовый статус. В шаблоне предусмотрено видимое оформление клавиатурного фокуса.

Полная перерисовка заменяет кнопки карточек. Чтобы после действия не терять точку клавиатурного управления, в заготовке дана функция `restoreTaskFocus(id, action)`: фокус возвращается на соответствующее действие той же задачи, а при исчезновении карточки — на активный фильтр. Её необходимо вызвать после успешного обновления и отрисовки. Смысл API фокуса: [HTMLElement.focus][dom-focus].

## 5. Модель и контракты модулей

### 5.1. Модель задачи из ПР2

```js
{
  id: 4,
  title: "Подготовить модель задач",
  completed: false,
  priority: "high"
}
```

Сохраняются правила ПР2: положительный безопасный целочисленный `id`, уникальный в списке; непустое нормализованное название длиной до 100; логический `completed`; приоритет `low`, `medium` или `high`. Общий контрольный набор содержит идентификаторы `[1, 4, 7, 10]`. Они намеренно не совпадают с индексами массива.

В этой работе наборы считаются корректными по модели ПР2. Проверки входа формы не добавляются, но идентификатор из DOM проверяется на границе обработчика.

### 5.2. Разделение ответственности

| Файл | Ответственность | Что не размещается |
|---|---|---|
| `data.js` | Общий и индивидуальный наборы, номер варианта. | Работа с DOM и изменение текущего списка. |
| `task-service.js` | Проверенные прикладные функции ПР2. | Кнопки, фильтр интерфейса и глобальный массив. |
| `task-selectors.js` | Вычисление выборки по фильтру. | Изменение входных задач и DOM. |
| `task-view.js` | Создание карточек, обновление списка, сводки и пустого состояния. | Изменение задач и подписки на события. |
| `main.js` | Текущее состояние, распознавание действий, вызовы сервиса и отрисовки. | Повторная реализация поиска, удаления и расчёта прогресса. |

### 5.3. Функции, реализуемые в ПР3

| Функция | Контракт |
|---|---|
| `getVisibleTasks(tasks, filter = "all")` | Возвращает новый массив: все задачи, невыполненные или выполненные. Допустимые значения `filter`: `all`, `pending`, `completed`. Порядок и входные записи сохраняются. |
| `createTaskElement(task)` | Возвращает новый элемент `li` с содержимым по разделу 6.2. Не добавляет его в общий список, не изменяет задачу и не назначает обработчики. |
| `renderTaskList(listElement, tasks)` | Заменяет дочерние карточки переданного списка. Сам `listElement` сохраняется. Повторный вызов не накапливает элементы. |
| `renderSummary(summaryElement, tasks, visibleCount)` | Через `getTaskStats` получает сводку полного массива и обновляет пять показателей. Процент выводится с одним знаком после точки и символом `%`. |
| `renderEmptyState(messageElement, total, visibleCount)` | Показывает установленное сообщение для пустого состояния либо очищает и скрывает его. |
| `renderApp()` | Вычисляет выборку и согласованно обновляет все части интерфейса. Не меняет `currentTasks` и не создаёт подписки. |
| `handleTaskListClick(event)` | Распознаёт действие и идентификатор, вызывает сервис, обрабатывает отказ либо сохраняет новый массив и обновляет интерфейс. |
| `handleFilterClick(event)` | Меняет только выбранный фильтр и обновляет отображение. Неизвестное значение фильтра игнорируется. |

Первые пять функций экспортируются из соответствующих модулей. Последние три остаются внутри `main.js`. Вывод текущего массива в глобальную переменную `window` для прохождения проверок не нужен.

Возвращаемое значение функций отрисовки и обработчиков не оценивается: проверяется изменение нужного представления. Для `getVisibleTasks` в обязательных прямых вызовах используются только три допустимых режима; недопустимое значение из DOM отсеивается в обработчике.

### 5.4. Результат операции ПР2

Успех:

```js
{ ok: true, tasks: /* новый массив */ }
```

Отказ:

```js
{ ok: false, error: "Понятное сообщение" }
```

При отказе нельзя присваивать `result.tasks` в `currentTasks`: такого массива в результате ошибки нет. Сообщение выводится в `#operation-message` через `textContent`; прежние данные остаются. После следующей успешной операции или корректного выбора фильтра сообщение очищается.

### 6.4. Задание 4. Фильтры, сводка и пустые состояния

В `task-selectors.js` реализовать `getVisibleTasks` для трёх режимов:

| Значение | Подпись | Результат |
|---|---|---|
| `all` | Все | Новый массив всех текущих задач. |
| `pending` | В работе | Только `completed === false`. |
| `completed` | Выполненные | Только `completed === true`. |

У всех режимов сохраняется исходный порядок. Пустой результат — обычный корректный массив `[]`. При фильтрации исходные объекты не изменяются.

В `main.js` реализовать `handleFilterClick` и `renderApp`. Кнопка фильтра находится через `closest`, поэтому нажатие на вложенный `span` также работает. Для текущего фильтра устанавливаются класс `is-active` и `aria-pressed="true"`, у остальных активность снимается.

**После каждого корректного выбора фильтра или успешного изменения задачи обновляются:** список карточек, сводка, количество показанных задач, пустое состояние и отметка активного фильтра.

В `task-view.js` реализовать `renderSummary`. В шаблоне используются следующие элементы:

| Селектор внутри `#task-summary` | Значение |
|---|---|
| `[data-stat="total"]` | Общее количество задач. |
| `[data-stat="completed"]` | Выполненные задачи во всём текущем массиве. |
| `[data-stat="pending"]` | Невыполненные задачи во всём текущем массиве. |
| `[data-stat="progress"]` | Прогресс всего списка с одним знаком после точки, например `50.0%`. |
| `[data-stat="visible"]` | Длина текущей видимой выборки. |

Для расчёта используется `getTaskStats(currentTasks)`, а не подсчёт карточек в DOM и не повторная формула в обработчике. При выборе «В работе» общий прогресс не становится нулевым: изменилась видимость, а не данные.

Реализовать `renderEmptyState`:

| Условие | Отображение |
|---|---|
| `total === 0`, `visibleCount === 0` | Сообщение `Список задач пуст.`; `hidden = false`. |
| `total > 0`, `visibleCount === 0` | Сообщение `Нет задач по выбранному фильтру.`; `hidden = false`. |
| `visibleCount > 0` | Пустой текст сообщения; `hidden = true`. |

При пустом массиве сводка содержит нули и `0.0%`, без `NaN` и `Infinity`. Пустое сообщение не вставляется в список как карточка задачи.

**Критерий готовности:** фильтры не теряют записи, состояние фильтра сохраняется после действий, счётчики согласованы и различаются два вида пустого состояния.

В отчёте необходимо добавить не менее трёх собственных сценариев, не совпадающих целиком с общим пошаговым сценарием. Каждый содержит исходное состояние, действия, ожидание и фактический результат.

Подходящие направления: единственная задача; все записи одного статуса; название длиной 100; несколько быстрых переключений; действие после перехода между фильтрами; неизменность экспортированного набора после пользовательских действий.

Минимум один сценарий относится к граничному состоянию, ещё один — к работе события или повторной отрисовки. Написание нового тестового фреймворка не требуется.

## 8. Индивидуальные варианты

Используется **тот же номер и тот же `variantTasks`, что в ПР2**. При переносе сохранены шесть задач с идентификаторами `[11, 23, 37, 41, 58, 64]`, исходными статусами и собственной тематикой. Приоритеты включают `low`, `medium` и `high`.

Если вариант ещё не назначен, порядок определения сохраняется из ПР2: для положительного порядкового номера `N` используется `((N - 1) % 8) + 1`; при отсутствии номера вариант определяется преподавателем.

Нажать ссылку «Свой вариант» в шапке либо открыть:

Служебное переключение по адресу уже есть в `main.js`. Оно выбирает исходный набор, а не сохраняет изменения. Пустой `variantTasks` является незаполненной заготовкой, а не выполненным вариантом.

**Сценарий индивидуального варианта:** после перезагрузки проверить исходную сводку, просмотреть все три фильтра, вернуться в «Все», переключить статус задачи `23`, удалить задачу `37`, проверить итоговую сводку и фильтры. Приоритет и название остальных записей сохраняются.

## 9. Дополнительное задание

После обязательной части можно выполнить одно из расширений. Оно не меняет модель ПР2 и поведение трёх основных фильтров.

### Вариант А. Дополнительный фильтр по приоритету

Добавить отдельную группу кнопок: все приоритеты, низкий, средний, высокий. Фильтры по статусу и приоритету применяются совместно. Например, «В работе» и «Высокий» показывают только невыполненные задачи высокого приоритета.

Общая сводка по-прежнему рассчитывается по полному массиву, а «Показано» — по совместной выборке. Необходимо проверить отсутствие совпадений, возврат обоих фильтров в исходное состояние и сохранение выбора после действия.

Три основные кнопки остаются в `#task-filters`; новую группу необходимо разместить отдельно, чтобы не менять контракт обязательной части.

### Вариант Б. Однократная отмена последнего удаления

Добавить отдельную кнопку «Отменить удаление». Отмена возвращает последнюю удалённую задачу с исходным статусом, приоритетом и на прежнюю позицию. После отмены кнопка снова недоступна. Новое удаление заменяет предыдущую возможность отмены; изменения статусов других задач не отменяются.

При восстановлении нельзя просто возвращать весь старый массив: это потеряет изменения, сделанные после удаления. Необходимо проверить удаление первой, средней и последней записи, удаление последней оставшейся задачи, смену фильтра перед отменой и невозможность повторной отмены.

Сохранение истории между перезагрузками не требуется. Дополнительная логика выделяется отдельно; `removeTask` из ПР2 сохраняет исходный контракт.

Для выбранного расширения в отчёте указываются правила поведения и не менее трёх собственных проверок. Изменение цветов, установка библиотеки или увеличение числа карточек сами по себе расширением не считаются.

## 12. Частые ошибки

| Симптом | Что проверить |
|---|---|
| При открытии файла модули не загружаются. | Адрес начинается с `http://127.0.0.1`, а не с `file://`; сервер работает. |
| В браузере ошибка импорта. | Расширения `.js`, регистр имён, относительные пути и наличие экспортов. |
| `document is not defined` в терминале. | Интерфейсный модуль запускается в браузере, а не через `node src/main.js`. |
| В Console ошибка обращения к `null`. | Совпадение селекторов с HTML и наличие требуемых контейнеров. |
| `findTaskById` не находит существующую задачу. | Идентификатор из `dataset` преобразован в число и не принят за индекс. |
| Нажатие на поле кнопки работает, а на текст — нет. | Поиск кнопки через `closest`, а не чтение `dataset` непосредственно у `target`. |
| После фильтра «Все» записи не возвращаются. | Полный `currentTasks` не заменён видимой выборкой. |
| После выполнения задача остаётся в «В работе». | После изменения заново рассчитан фильтр и вызвана отрисовка. |
| Удалённая карточка возвращается. | Обновлены данные через `removeTask`, а не только удалён DOM-узел. |
| После действий счётчики неправильные. | Сводка берётся из полного массива, а результат сервиса действительно сохранён. |
| После обновлений растёт количество карточек. | Используется замена содержимого, а не бесконечное добавление к старому списку. |
| Обработчики перестают работать после рендера. | Сохранён сам контейнер `ul`; заменяются только его дочерние элементы. |
| Одно нажатие вызывает несколько изменений. | Новые анонимные обработчики не назначаются при каждой отрисовке. |
| В названии появилась разметка. | Используется `textContent`, а не HTML-интерпретация строки. |
| При фильтрации исчезает общая статистика. | В `renderSummary` передан `currentTasks`, а не `visibleTasks`. |
| После перезагрузки всё сбрасывается. | Для ПР3 это ожидаемо; сохранение реализуется в ПР4. |
| Пустой индивидуальный набор проходит как вариант. | Перенесены заполненные `variantTasks` и `variantNumber` из ПР2. |

Правила DOM, модулей и событий приведены в разделе 4 и документации ниже. Для диагностики конкретной ошибки необходимо сначала воспроизвести минимальное действие, а затем исследовать значения через точку останова.
