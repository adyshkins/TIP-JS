## 1. Цель и результат работы

**Цель работы** — освоить обработку HTML-форм, разделить нативную и прикладную валидацию, организовать режимы создания и редактирования и безопасно сохранять состояние браузерного приложения.

Для выполнения работы необходимо научиться:

- обрабатывать событие `submit` и отменять стандартную отправку формы;
- получать значения полей через `FormData` и учитывать их строковый формат;
- сочетать ограничения HTML с прикладными правилами модели;
- показывать ошибки около соответствующих полей и очищать их после исправления;
- использовать одну форму в режимах создания и редактирования;
- сериализовать данные в JSON и сохранять их в `localStorage`;
- проверять прочитанные данные до использования и восстанавливаться после ошибок;
- сохранять результат каждой успешной операции, не смешивая данные разных наборов;
- повторно проверять ранее реализованное поведение после расширения приложения.

**Итоговое приложение:** список задач из ПР3 с формой добавления и редактирования, фильтрами, изменением статуса, удалением, сводкой, восстановлением данных после перезагрузки и явным сбросом к исходному набору.

## 4. Теоретические сведения

### 4.1. Форма и событие `submit`

Форма объединяет связанные поля и поддерживает отправку с клавиатуры. Основная логика привязывается к событию `submit` самой формы, а не только к `click` кнопки:

```js
form.addEventListener("submit", (event) => {
  event.preventDefault();
  // Чтение и проверка данных.
});
```

`preventDefault()` отменяет стандартное действие браузера — переход или отправку документа. Событие при этом продолжает существовать; прикладная обработка выполняется дальше. Нажатие Enter в подходящем поле также может инициировать отправку, поэтому обработка только клика не покрывает обычное поведение формы.

Кнопкам, которые не отправляют форму, явно задаётся `type="button"`. Кнопка основного действия имеет `type="submit"`.

### 4.2. Нативные ограничения HTML

В шаблоне используются `required`, `min`, `step` и `maxlength`. Браузер умеет проверить эти ограничения до события `submit` и показать встроенное сообщение.

```html
<input name="id" type="number" min="1" step="1" required>
<input name="title" maxlength="100" required>
```

Нативная проверка не знает правил предметной области. Она не определяет, занят ли идентификатор другой задачей, и считает строку из пробелов непустой. Поэтому одного HTML недостаточно.

Методы `checkValidity()` и `reportValidity()` возвращают результат проверки; `reportValidity()` дополнительно инициирует показ сообщений браузера. Через `setCustomValidity(message)` можно установить прикладную ошибку. После исправления значение необходимо сбросить вызовом `setCustomValidity("")`, иначе поле останется невалидным.

### 4.3. `FormData` и типы значений

Объект `FormData` собирает успешные элементы управления с атрибутом `name`:

```js
const formData = new FormData(form);
const rawId = formData.get("id");
const rawTitle = formData.get("title");
```

Обычные значения формы читаются строками. Числовой вид поля не превращает значение автоматически в JavaScript-число. Граница преобразования должна быть явной:

```js
const id = Number(rawId);
```

Отключённое поле (`disabled`) не включается в `FormData`. В режиме редактирования поле id заблокировано, поэтому идентификатор берётся из переменной `editingId`, а не повторно из формы.

### 4.4. Два уровня проверки ввода

В ПР4 используются два взаимодополняющих уровня:

| Уровень | Примеры | Назначение |
|---|---|---|
| HTML Constraint Validation | `required`, `min`, `step`, `maxlength` | Быстрая проверка структуры ввода и стандартное клавиатурное поведение. |
| Прикладная проверка | уникальность id, `trim`, допустимый приоритет, наличие редактируемой задачи | Правила конкретной модели и понятные ошибки полей. |

Даже после проверки формы вызывается функция сервиса `addTask` или `updateTask`. Валидация интерфейса улучшает обратную связь, но не отменяет защиту прикладной операции. В дальнейшем сервер также будет проверять данные независимо от клиента.

`validateTaskDraft` является чистой функцией: она не обращается к DOM, не показывает сообщения и не меняет входные значения. Такой код проще проверять и повторно использовать.

### 4.5. Режимы создания и редактирования

Одна форма работает в двух режимах:

```text
Создание: editingId === null
Редактирование: editingId === id существующей задачи
```

В режиме создания id доступен, поля после успеха очищаются, а операция выполняется через `addTask`. В режиме редактирования id показывается, но заблокирован; название и приоритет заполняются из текущей задачи, а операция выполняется через `updateTask`.

Режим — часть состояния интерфейса, но не часть модели задачи. Он не сохраняется в `localStorage`. После перезагрузки форма открывается в режиме создания.

### 4.6. `localStorage` и строковое хранение

`localStorage` хранит пары «ключ — строка» для origin страницы. Запись сохраняется между обычными перезагрузками и сеансами браузера, пока не будет удалена пользователем, приложением или настройками среды.

```js
storage.setItem(key, JSON.stringify(value));
const raw = storage.getItem(key);
```

`getItem` возвращает строку либо `null`, если ключ отсутствует. Массив нельзя считать сохранённым как JavaScript-объект: для записи используется `JSON.stringify`, для чтения — `JSON.parse`.

Web Storage выполняет операции синхронно. В этой учебной работе объём данных мал. Для больших наборов или сложной автономной модели потребовался бы другой механизм, но это не входит в обязательный объём.

### 4.7. JSON не подтверждает корректность данных

Успешный `JSON.parse` означает только корректный синтаксис JSON. Полученное значение может оказаться числом, объектом другой версии, массивом с повторяющимися id или задачами с неверными полями.

В хранилище записывается оболочка:

```json
{
  "version": 1,
  "tasks": []
}
```

После разбора необходимо проверить:

- точное значение `version`;
- наличие массива `tasks`;
- положительный безопасный целочисленный и уникальный `id`;
- нормализованное непустое название длиной до 100 символов;
- логический `completed`;
- приоритет `low`, `medium` или `high`.

Некорректное значение не используется частично. Приложение получает независимую копию исходного набора и показывает предупреждение. Повреждённая запись автоматически не удаляется: её можно исследовать в DevTools, а затем удалить кнопкой сброса.

### 4.8. Ошибки доступа к хранилищу

Чтение и запись могут завершиться исключением: например, из-за политики браузера, режима конфиденциальности или ограничения объёма. Поэтому граница `localStorage` помещается в отдельный модуль и перехватывает исключения.

Функции возвращают результат:

```js
{ ok: true }
```

или:

```js
{ ok: false, error: "Понятное сообщение" }
```

Успешное изменение задачи не откатывается только из-за невозможности записи: оно остаётся в памяти текущей вкладки, а пользователь получает предупреждение, что после перезагрузки результат может быть потерян.

### 4.9. Поток данных приложения

Начальная загрузка:

```text
Исходный набор + ключ
          ↓
      loadTasks
     ↙         ↘
storage         fallback
     ↘         ↙
     currentTasks
          ↓
       renderApp
```

Успешная операция:

```text
submit или click
       ↓
валидация границы
       ↓
функция сервиса
       ↓ ok
новый currentTasks
       ↓
saveTasks → renderApp
```

`renderApp` не читает и не записывает хранилище. Повторная отрисовка не должна создавать побочные эффекты или новую запись JSON.

### 4.10. Ключи наборов и проверок

Основное приложение использует два независимых ключа:

```text
tip-js-practice-04:demo
tip-js-practice-04:variant
```

Поэтому изменения общего набора не появляются в индивидуальном и наоборот. Страница автоматических проверок открывает приложение с `mode=check`; для неё предусмотрены отдельные ключи `tip-js-practice-04:checks:*`. Проверки не должны удалять рабочие данные.

В приложении не используется `localStorage.clear()`: эта команда затрагивает все ключи текущего origin, в том числе данные других учебных страниц. Сброс удаляет только рассчитанный `storageKey`.

## 5. Модель и контракты модулей

### 5.1. Модель задачи

Модель ПР2 сохраняется:

```js
{
  id: 4,
  title: "Подготовить модель задач",
  completed: false,
  priority: "high"
}
```

Правила: `id` — положительное безопасное целое и уникален в массиве; `title` — нормализованная непустая строка длиной до 100; `completed` — boolean; `priority` — `low`, `medium` или `high`.

### 5.2. Распределение ответственности

| Файл | Ответственность | Что не размещается |
|---|---|---|
| `data.js` | Исходные общий и индивидуальный наборы. | Текущее состояние и сохранённые изменения. |
| `task-service.js` | Создание и неизменяющие входной массив операции над задачами. | DOM, поля формы и `localStorage`. |
| `task-selectors.js` | Видимая выборка по фильтру. | Изменение данных и сохранение. |
| `task-view.js` | Создание карточек, списка, сводки и пустого состояния. | Обработчики, изменение модели и запись JSON. |
| `form-validation.js` | Нормализация и чистая проверка черновика формы. | Показ ошибок и вызов сервисной операции. |
| `task-storage.js` | Схема сохранённых данных, JSON и обработка ошибок хранилища. | DOM, фильтры и редактирование формы. |
| `main.js` | Текущее состояние, режим формы, события, координация сервиса, хранения и отображения. | Повторная реализация правил модели и ручная сборка карточек. |

### 5.3. `updateTask`

```js
updateTask(tasks, id, title, priority)
```

Успех:

```js
{ ok: true, tasks: /* новый массив */ }
```

Функция проверяет id, наличие задачи, название и приоритет. В выбранной задаче меняются только `title` и `priority`; `id` и `completed` сохраняются. Исходный массив и его объекты не изменяются. Для проверки полей можно переиспользовать `createTask`, но создаваемое им значение `completed: false` не должно сбросить настоящий статус редактируемой задачи.

При некорректных данных или отсутствии id возвращается `{ ok: false, error }` без частичного результата.

### 5.4. `validateTaskDraft`

```js
validateTaskDraft(draft, tasks, editingId = null)
```

Черновик содержит `{ id, title, priority }`. В режиме создания id преобразуется в число, проверяется и сравнивается с текущими задачами. В режиме редактирования источником id является `editingId`, а наличие соответствующей задачи обязательно.

Успех:

```js
{
  ok: true,
  value: { id: 20, title: "Изучить localStorage", priority: "high" }
}
```

Отказ:

```js
{
  ok: false,
  errors: {
    id: "...",
    title: "...",
    priority: "..."
  }
}
```

Объект `errors` содержит только поля с ошибками. При нескольких независимых ошибках они возвращаются вместе. Формулировки могут отличаться, но должны быть непустыми и понятными.

### 5.5. Функции хранения

| Функция | Контракт |
|---|---|
| `isValidTaskList(value)` | Возвращает boolean после проверки всего массива и уникальности id. Не исправляет значение. |
| `loadTasks(storage, key, fallbackTasks)` | Возвращает новый массив из корректной записи либо независимую копию fallback. Исключения наружу не выпускаются. |
| `saveTasks(storage, key, tasks)` | Проверяет список и записывает `{ version: 1, tasks }`. Некорректный список не записывается. |
| `removeSavedTasks(storage, key)` | Удаляет ровно один ключ и возвращает результат операции. |

Результат `loadTasks` различает источники:

| Состояние | `ok` | `source` | Данные |
|---|---:|---|---|
| Ключ отсутствует | `true` | `initial` | Копия исходного набора. |
| Корректная запись | `true` | `storage` | Новая копия сохранённых задач. |
| Ошибка чтения, JSON, версии или схемы | `false` | `fallback` | Копия исходного набора и `error`. |

Передача `storage` аргументом позволяет проверять модуль с объектом-имитацией и явно показывает внешнюю зависимость.

### 6.5. Задание 5. Модуль локального хранения

В `task-storage.js` реализовать четыре функции из раздела 5.5.

Для `isValidTaskList` необходимо проверить весь массив. Если хотя бы одна запись некорректна или id повторяется, возвращается `false`. Нормализация при чтении не выполняется: данные либо соответствуют сохранённой схеме, либо отклоняются целиком.

`loadTasks` выполняет последовательность:

1. Создаёт независимую копию `fallbackTasks`.
2. Внутри `try` вызывает `storage.getItem(key)`.
3. Для `null` возвращает исходную копию с `source: "initial"`.
4. Разбирает JSON и проверяет версию и задачи.
5. Для корректной записи возвращает новую копию с `source: "storage"`.
6. Для исключения или неверной схемы возвращает fallback с непустой ошибкой.

`saveTasks` сначала проверяет список. Затем внутри `try` создаёт JSON-оболочку и вызывает `setItem`. `removeSavedTasks` аналогично перехватывает ошибку `removeItem`.

Необходимо использовать переданный объект `storage`, а не скрыто обращаться к глобальному `localStorage` внутри модуля. `localStorage.clear()` не используется.

**Критерий готовности:** корректные данные проходят круг «сохранить — прочитать», а повреждённые данные и исключения приводят к управляемому результату.

| Хорошо / 4 | Выполнены все обязательные задания и вариант; проходят проверки; операции сохраняются, ошибки обрабатываются, отчёт заполнен. |
| Отлично / 5 | Выполнено всё для «4», добавлено содержательное расширение с проверками; на защите объясняются границы валидации и самостоятельно вносится изменение. |

«Отлично» предполагает защиту. Успешный протокол без понимания потока данных не является достаточным основанием.

На защите может потребоваться: добавить или отредактировать задачу; объяснить отсутствие disabled-поля в `FormData`; воспроизвести повторный id; показать JSON в DevTools; повредить запись; объяснить fallback; изменить версию схемы; доказать разделение ключей; обработать ошибку записи.

## 12. Частые ошибки

| Симптом | Что проверить |
|---|---|
| Enter перезагружает страницу. | Обрабатывается `submit` формы и вызывается `preventDefault`. |
| Кнопка отмены отправляет форму. | У неё указан `type="button"`. |
| Числовой id остаётся строкой. | Значение `FormData` явно преобразуется через `Number`. |
| Пустой id превращается в `0`. | Пустая строка отклоняется до или вместе с числовой проверкой. |
| Пробелы проходят `required`. | Выполняется прикладной `trim` и проверка длины. |
| После ошибки поле всегда невалидно. | На `input` вызывается `setCustomValidity("")`. |
| При редактировании `FormData.get("id")` возвращает `null`. | Disabled-поле не отправляется; используется `editingId`. |
| При редактировании сбрасывается статус. | `updateTask` сохраняет настоящий `completed`. |
| Изменение одной задачи меняет массив ПР3. | Операция возвращает новый массив и новый изменённый объект. |
| После перезагрузки возвращаются исходные данные. | Успешная операция вызывает `saveTasks`; адрес и порт не менялись. |
| В storage видно `[object Object]`. | Перед `setItem` используется `JSON.stringify`. |
| Повреждённый JSON ломает весь запуск. | `JSON.parse` находится внутри `try/catch`, используется fallback. |
| Любой JSON считается корректным. | После разбора проверяются версия и полная схема задач. |
| Общий набор появляется в варианте. | Для `demo` и `variant` рассчитаны разные ключи. |
| Проверки удаляют рабочие данные. | Для `mode=check` используются отдельные ключи. |
| Сброс удаляет данные других страниц. | Используется `removeItem(storageKey)`, а не `clear()`. |
| Фильтр создаёт запись в storage. | Сохраняются только изменения модели, не режим отображения. |
| Отрисовка многократно записывает JSON. | `renderApp` не содержит `saveTasks`. |
| После сброса ключ сразу появляется снова. | Исходный набор не сохраняется повторно в обработчике сброса. |
| При другом порте «пропали» данные. | Другой порт означает другой origin и отдельное хранилище. |
