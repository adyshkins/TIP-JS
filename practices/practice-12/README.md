# Практическая работа № 12. Подключение API к базе данных

**Дисциплина:** «Технологии индустриального программирования»<br>
**Стек:** Node.js 24.x, Express 5, PostgreSQL 18.x, `pg`<br>
**Продолжительность:** 2 академических часа<br>
**Форма работы:** индивидуальная<br>
**Результат:** Express API из ПР10, использующий PostgreSQL вместо массива в памяти<br>
**Предыдущие работы:** ПР10 — CRUD API; ПР11 — схема, исходные данные и SQL-запросы

> ПР11 создала связанные таблицы `categories` и `tasks`, но сервер их не использовал. В ПР12 HTTP-контракт сохраняется, а операции хранилища заменяются асинхронными параметризованными запросами. Созданные и изменённые записи должны оставаться после остановки и повторного запуска API.

## 1. Цель и результат

Цель работы — освоить подключение серверного приложения к реляционной базе данных и провести границу между HTTP-слоем, предметной валидацией и постоянным хранилищем.

После выполнения должен работать следующий путь данных:

`React-клиент → HTTP API → PostgreSQL-хранилище → пул pg → PostgreSQL`.

Необходимо:

- настроить соединение через переменные окружения, не записывая пароль в Git;
- использовать один пул соединений на процесс приложения;
- реализовать чтение и CRUD через `async/await`;
- передавать пользовательские значения только параметрами `$1`, `$2`, …;
- сохранить JSON-поля `categoryId`, хотя в таблице используется `category_id`;
- сохранить буквальную семантику фильтра `q`, включая символы `%`, `_` и `\`;
- выполнить учебный reset в транзакции на одном клиенте;
- преобразовать ожидаемые ошибки базы в безопасные ошибки API;
- подтвердить постоянство данных автоматическими и ручными проверками.

ORM, Docker, аутентификация, миграционный фреймворк и развёртывание в этой работе не требуются. Они не должны заменять понимание SQL и драйвера.

**Предлагаемый формат:** 90 минут после завершения ПР10–ПР11 и предварительной установки PostgreSQL; отчёт, вариант и расширенный ручной протокол могут быть завершены самостоятельно.

| Этап | Ориентир | Результат |
|---|---:|---|
| Подготовка | 10 минут | База, `.env`, зависимости и проверка соединения. |
| Чтение | 20 минут | Список, фильтры, категории и задача по id. |
| Запись | 25 минут | INSERT, динамический UPDATE и DELETE. |

## 4. Архитектура доступа к данным

Маршрут не должен содержать SQL. Он разбирает HTTP-ввод, вызывает предметную валидацию, обращается к `store` и формирует HTTP-ответ. Хранилище не должно знать о `req`, `res`, статусах HTTP и CORS. Пул отвечает за повторное использование подключений.

| Слой | Получает | Возвращает | Не должен делать |
|---|---|---|---|
| `routes.js` | HTTP-запрос | HTTP-ответ | Склеивать SQL, читать пароль. |
| `task-validation.js` | JSON-значение | Нормализованный объект | Обращаться к Express или выполнять SQL. |
| `query-builders.js` | Проверенные фильтры/изменения | `{ text, values }` | Открывать соединение. |
| `store.js` | Предметные значения | Объекты задач/категорий | Формировать HTTP-ответ. |
| `db.js` | Строку подключения | `Pool` | Создавать пул на каждый запрос. |

`createApp` получает хранилище как зависимость. Благодаря этому HTTP-контракт проверяется быстрым тестовым хранилищем, а SQL — отдельно. Настоящее приложение передаёт `createPostgresStore(pool)`.

Все методы PostgreSQL-хранилища асинхронны. В Express 5 отклонённый Promise асинхронного обработчика передаётся обработчику ошибок; дополнительная обёртка `try/catch` вокруг каждого маршрута не требуется. Ожидаемые ошибки всё равно должны преобразовываться централизованно.

## 5. Пул и жизненный цикл процесса

Веб-приложение выполняет много коротких запросов. Создавать новое физическое соединение для каждого HTTP-запроса не следует. В `db.js` создаётся один ограниченный `Pool`, а обычные одиночные запросы выполняются через `pool.query(...)`.

При старте сервер:

1. проверяет конфигурацию;
2. создаёт один пул;
3. выполняет `store.ping()`;
4. начинает слушать HTTP-порт только после успешного соединения.

При `SIGINT` или `SIGTERM` сначала прекращается приём HTTP-запросов, затем вызывается `pool.end()`. Это освобождает соединения и таймеры. Обработчик `pool.on('error', ...)` нужен для ошибок простаивающих клиентов, которые не связаны с конкретным ожидаемым `await pool.query(...)`.

`GET /api/health` подтверждает доступность базы ответом:

```json
{"data":{"status":"ok","database":"connected"}}
```

В ответ не выводятся строка подключения, роль, адрес сервера, SQL и текст исключения драйвера.

## 6. Параметризованные запросы

Пользовательские значения нельзя объединять с SQL через шаблонные строки:

```js
// Неверно: значение меняет текст SQL.
`SELECT ... WHERE title = '${title}'`
```

Значение передаётся отдельно:

```js
const result = await pool.query(
  'SELECT id, title FROM public.tasks WHERE id = $1',
  [id],
);
```

Параметры применяются к значениям, но не к именам таблиц, колонок и направлению сортировки. Поэтому динамические части запроса в работе выбираются только из заранее заданных фрагментов. Принимаемые от клиента имена колонок в SQL не вставляются.

### 6.1. Отображение имён

Внешний контракт сохраняет camelCase:

```sql
category_id AS "categoryId"
```

Для всех операций возвращается один и тот же набор:

```text
id, title, completed, priority, category_id AS "categoryId"
```

Если убрать двойные кавычки, PostgreSQL приведёт алиас к нижнему регистру и клиент получит `categoryid`, что нарушит контракт.

### 6.2. Фильтры списка

`buildListTasksQuery(filters)` формирует условия в фиксированном порядке:

1. `completed`;
2. `priority`;
3. `category_id`;
4. `title ILIKE` для `q`.

Номер параметра определяется длиной `values`. Пустые фильтры дают SELECT без WHERE. Запрос всегда завершается `ORDER BY id`.

Фильтр `q` в ПР10 означал буквальное вхождение подстроки. В SQL символы `%` и `_` являются шаблонами, а `\` используется для экранирования. Поэтому перед добавлением внешних `%` функция `escapeLikePattern` экранирует все три символа, а условие содержит `ESCAPE '\'`.

Пример для `q=50%_готово`:

```text
SQL:    title ILIKE $1 ESCAPE '\'
values: ['%50\%\_готово%']
```

Строка поиска остаётся в `values`, а не появляется в `text`.

### 6.3. Динамический PATCH

PATCH изменяет только переданные поля. `buildUpdateTaskQuery(id, changes)` собирает `SET` из разрешённого фиксированного списка:

| JSON | SQL |
|---|---|
| `title` | `title` |
| `completed` | `completed` |
| `priority` | `priority` |
| `categoryId` | `category_id` |

Порядок не зависит от порядка ключей входного JSON. Значение `false` определяется через наличие свойства, а не через truthy-проверку. `id` добавляется последним параметром в WHERE. Пустой объект и неизвестные поля отклоняются до запроса.

## 7. Методы PostgreSQL-хранилища

Заменить TODO в `src/query-builders.js` и `src/store.js`.

### 7.1. Чтение

- `listCategories()` — `SELECT id, name ... ORDER BY id`;
- `listTasks(filters)` — запрос от `buildListTasksQuery`;
- `getTask(id)` — параметризованный SELECT; первая строка или `null`;
- `ping()` — короткий запрос `SELECT 1 AS ok`.

`result.rows` всегда является массивом. Отсутствующая строка определяется как `result.rows[0] ?? null`, а не как ошибка базы.

### 7.2. Создание

POST принимает `title`, `priority`, `categoryId`. Поле `completed` в INSERT не передаётся: база назначает `DEFAULT false`. `id` назначает identity. Запрос использует `RETURNING`, поэтому дополнительный SELECT не нужен.

Значение нового id нельзя вычислять как `count(*) + 1`, `max(id) + 1` или в JavaScript. Между параллельными запросами такие вычисления создают конфликт. Identity/sequence является источником id.

### 7.3. Обновление

`updateTask(id, changes)` выполняет запрос от builder и возвращает строку `RETURNING`. Если между предварительным GET middleware и UPDATE запись была удалена, `rows` пуст; метод возвращает `null`, а маршрут формирует 404.

Такой повторный контроль не устраняет все конкурентные конфликты, но не выдаёт успешный ответ для фактически отсутствующей записи.

### 7.4. Удаление

`deleteTask(id)` выполняет `DELETE ... WHERE id = $1`. Результат определяется по `rowCount === 1`. DELETE не уменьшает sequence и не делает id доступным повторно.

## 8. Транзакция учебного reset

Reset восстанавливает 3 категории и 12 задач. Он нужен только для локальных проверок сквозного клиента и включается через `ENABLE_DEBUG_RESET=true`. При `false` маршрут `/api/debug/reset` не регистрируется.

Reset изменяет несколько таблиц и sequence, поэтому выполняется атомарно:

1. `const client = await pool.connect()`;
2. `BEGIN`;
3. удалить задачи, затем категории;
4. вставить исходные категории и задачи;
5. синхронизировать обе sequence;
6. `COMMIT`;
7. при ошибке — `ROLLBACK` и повторный `throw`;
8. в `finally` — `client.release()`.

Все команды транзакции должны выполняться **одним и тем же `client`**. Использование `pool.query('BEGIN')`, а затем других `pool.query(...)` не гарантирует одно соединение и не образует требуемую транзакцию.

Исходные значения находятся в `sql/02_seed.sql`. Допустимо вынести массивы seed в отдельный модуль, но нельзя читать SQL-файл по относительному пути при каждом HTTP-запросе. Для INSERT reset используются параметры или фиксированные предоставленные значения; данные запроса пользователя туда не попадают.

Reset возвращает:

```json
{"data":{"reset":true,"total":12}}
```

Этот маршрут нельзя считать административным API для эксплуатации. В итоговом развёртывании его следует отключить. Публичный reset без авторизации способен уничтожить данные.

## 9. Ошибки базы и HTTP

PostgreSQL передаёт пятисимвольный `SQLSTATE` в поле `error.code`. Приложение анализирует код, а не локализованный текст сообщения.

| Ситуация | SQLSTATE | Ответ API |
|---|---|---|
| Несуществующий внешний ключ | `23503` | 400 `VALIDATION_ERROR` для категории. |
| NOT NULL / CHECK / длина | `23502`, `23514`, `22001` | 400 `VALIDATION_ERROR`. |
| Ошибка соединения | класс `08`, также остановка сервера `57P01` | 503 `DATABASE_UNAVAILABLE`. |
| Неожиданная ошибка | другая | 500 `INTERNAL_ERROR`. |

Валидация приложения выполняется до SQL и даёт понятные поля `details`. Ограничения базы остаются второй линией защиты и закрывают гонку: категория может быть удалена после её предварительного чтения, но до INSERT/UPDATE.

Ответ не должен содержать пароль, SQL, stack trace, имя constraint, `detail` или полный текст драйвера. Подробность сохраняется в серверном журнале только там, где это допустимо; стартовый проект отдаёт безопасное обобщённое сообщение.

## 11. Индивидуальные варианты

Номер сохраняется из предыдущих работ; номер больше восьми приводится по формуле `((номер - 1) % 8) + 1`. Все варианты выполняют полный CRUD и дополнительный сценарий. Перед сценарием восстановить исходный набор, после — проверить результат и через API, и прямым SELECT в psql.

| Вариант | Начальная выборка | Сценарий и ожидаемый результат |
|---:|---|---|
| 1 | `completed=false` | Создать задачу, завершить PATCH, перезапустить API; запись сохранена и исчезает из активной выборки. |
| 2 | `completed=true` | Переименовать выполненную задачу, перезапустить API; новое название и статус сохранены. |
| 3 | `priority=high` | Создать high, изменить на low; после перезапуска запись не входит в high и входит в low. |
| 4 | `priority=medium` | Создать, удалить, перезапустить API и создать следующую; новый id больше удалённого. |
| 5 | `categoryId=1` | Создать в категории 1, перенести в 2; после перезапуска `GET /tasks/:id` содержит categoryId 2. |
| 6 | `q=%_` | Создать название с буквальными `%_`; поиск `%_` находит его как текст, а не как два wildcard. |
| 7 | без фильтра | Отправить два POST почти одновременно; получены разные id, обе записи остаются после перезапуска. |
| 8 | в работе, high, категория 2 | Создать подходящую задачу, завершить, перезапустить, найти по id и удалить; подтверждена цепочка POST → PATCH → restart → GET → DELETE. |

Для каждого варианта дополнительно отправить неверный запрос напрямую и подтвердить отсутствие частичного изменения. В отчёте привести методы, пути, тела без секретов, статусы, фактические id, SELECT проверки и поведение интерфейса.

## 12. Проверки

### 12.1. Автоматические наборы

Из `practice-12`:

```bash
npm run check:queries
npm run check:api
npm run check:db
npm test
```

| Набор | Назначение |
|---|---|
| `check:queries` | Builder, параметризация, store, транзакция и освобождение клиента. |
| `check:api` | Асинхронный HTTP-контракт, валидация, CORS, reset и безопасные ошибки. |
| `check:db` | CRUD и фильтры на реальной базе из локального `DATABASE_URL`. |
| `npm test` | Все тестовые файлы; DB-тест пропускается, если окружение не содержит `DATABASE_URL`. |

В завершённом решении ожидаются 26 успешных тестов при доступной отдельной учебной базе. Без `DATABASE_URL` один DB-тест помечается skipped; это не заменяет обязательный `npm run check:db`.

DB-проверка изменяет учебную базу и восстанавливает исходный набор в `finally`. Не направлять её на общую, рабочую или чужую базу. При аварийном завершении проверить данные вручную и выполнить reset осознанно.

### 12.2. Прямые HTTP-запросы

Создать временный `task.json` в UTF-8:

```json
{"title":"Проверить PostgreSQL","priority":"high","categoryId":2}
```

При запущенном API:

```bash
curl -i -X POST "http://127.0.0.1:5505/api/tasks" -H "Content-Type: application/json" --data-binary "@task.json"
```

В Windows PowerShell использовать `curl.exe`. Фактический id взять из ответа; не подставлять 35 вслепую, поскольку sequence могла продвинуться.

Создать `patch.json` с `{"completed":true}`, затем выполнить для фактического id:

```bash
curl -i -X PATCH "http://127.0.0.1:5505/api/tasks/35" -H "Content-Type: application/json" --data-binary "@patch.json"
curl -i "http://127.0.0.1:5505/api/tasks/35"
```

Остановить и снова запустить API, повторить GET. После проверки удалить запись:

```bash
curl -i -X DELETE "http://127.0.0.1:5505/api/tasks/35"
```

## 13. Типичные ошибки

| Проявление | Причина и исправление |
|---|---|
| `password authentication failed` | Неверная роль/пароль или подключение не к тому экземпляру; проверить psql без публикации секрета. |
| `relation "tasks" does not exist` | Выбрана другая база или схема ПР11 не применена. |
| `ECONNREFUSED` | Служба/порт PostgreSQL недоступны; проверить адрес и порт. |
| API запускается, но данные ПР10 | Запущен старый процесс или маршрут использует прежний memory store. |
| В JSON приходит `categoryid` | Алиас не заключён в двойные кавычки. |
| Фильтр `%` возвращает всё | Вход не экранирован перед ILIKE. |
| Ошибка около `$1` для имени колонки | Параметры применяются к значениям, не идентификаторам. |
| SQL injection остаётся возможной | Значение вставлено в `text`, а не передано через `values`. |
| PATCH с `false` ничего не меняет | Используется truthy-проверка вместо `Object.hasOwn`. |
| После PATCH потерялись поля | Выполнена замена строки или SET содержит отсутствующие поля. |
| Reset иногда фиксирует половину данных | Команды выполнены разными клиентами либо отсутствует ROLLBACK. |
| После нескольких reset запросы зависают | `client.release()` не находится в `finally`, пул исчерпан. |
| Тесты завершаются, но Node не выходит | Пул не закрыт через `pool.end()`. |
| Новый id не равен 35 | Sequence уже продвинулась; точное значение после проверок не гарантируется. |
| `.env` виден в Git | Файл добавлен до `.gitignore`; удалить из индекса без удаления локального файла и сменить раскрытый пароль. |
