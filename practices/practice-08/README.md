## 1. Цель и результат

**Цель работы** — организовать взаимодействие компонентного интерфейса с HTTP API: загрузку при изменении зависимостей, очистку эффекта, операции изменения и повторное получение актуальных данных.

После выполнения приложение:

- получает задачи и категории с сервера;
- передаёт фильтры в query-параметрах, а не фильтрует только уже загруженный массив;
- создаёт, редактирует, переключает статус и удаляет задачи через API;
- различает загрузку, пустой успешный ответ и ошибку;
- сохраняет последний успешный результат при ошибке обновления;
- отменяет ненужные запросы и игнорирует запоздавшие ответы;
- не создаёт две записи от повторного нажатия во время сохранения;
- сохраняет введённые значения при неуспешной записи;
- повторяет GET после подтверждённого изменения;
- проходит автоматизированные проверки и ручной протокол.

Обновление страницы больше не сбрасывает задачи, пока работает тот же процесс API. После перезапуска API или команды восстановления исходный набор возвращается. База данных на этом этапе отсутствует.

## 4. Контракт API и переход от ПР7

### 4.1. Методы

| Метод и путь | Результат |
|---|---|
| `GET /api/tasks` | `200`, `{ data: task[], meta: { total, filters } }` |
| `GET /api/categories` | `200`, `{ data: category[], meta }` |
| `GET /api/tasks/:id` | `200`, `{ data: task }` |
| `POST /api/tasks` | `201`, `{ data: task }` |
| `PATCH /api/tasks/:id` | `200`, `{ data: task }` |
| `DELETE /api/tasks/:id` | `204`, без тела |
| `POST /api/debug/reset` | `200`, `{ data: { reset: true, total: 12 } }` |

При создании отправляются только `title`, `priority`, `categoryId`. Сервер назначает `id` и `completed: false`. Редактирование формы передаёт эти же три поля, смена статуса — `{ completed: boolean }`.

```js
// Задача
{ id: 4, title: 'Подготовить модель задач', completed: false, priority: 'high', categoryId: 2 }
```

Название: 1–100 единиц `length` JavaScript-строки после `trim`. Приоритет: `low`, `medium`, `high`. Категория: существующий положительный целый id.

Ошибки сервера имеют вид `{ error: { code, message, details } }`. Клиент преобразует их в `ApiError`, сохраняя `kind`, `status`, `code`, `details`. Ответ 204 преобразуется в `null` без вызова `response.json()`.

### 4.2. Фильтры

Форма хранит строки:

```js
{ q: '', completed: '', priority: '', categoryId: '' }
```

Пустые значения исключаются при построении URL; строка `'false'` обязательно сохраняется. Например, вариант 8 вызывает:

```text
GET /api/tasks?completed=false&priority=high&categoryId=2
```

Сервер объединяет фильтры через И. Поиск — по названию, без учёта регистра. Неизвестные и повторяющиеся query-параметры отклоняются. Полный контракт приведён в [ПР6](../practice-06/README.md#4-контракт-учебного-api).

### 4.3. Что меняется

| ПР7 | ПР8 |
|---|---|
| Исходный набор импортируется в интерфейс | Набор доступен только серверу. |
| Локальные `addTask`, `updateTask`, `removeTask` | HTTP-методы предметного API. |
| Id назначает локальная функция | Id назначает сервер. |
| `selectTasks` фильтрует массив | Фильтры передаются серверу. |
| `onSave` возвращает boolean | `onSave` возвращает `Promise<boolean>`. |
| Общая статистика всего локального массива | Статистика **последней полученной выборки**. |
| Перезагрузка страницы сбрасывает задачи | Данные сохраняются в памяти процесса API. |

`meta.total` — число задач после серверных фильтров, а не размер всей базы. Поэтому надпись «Всего задач в системе» для этого значения неверна. В предоставленном интерфейсе явно указана последняя полученная выборка.

## 5. Теория: React и асинхронная работа

### 5.1. Эффект и зависимости

`useEffect` синхронизирует компонент с внешней системой после обновления интерфейса. При изменении зависимостей React сначала вызывает cleanup прежнего эффекта, затем запускает новый; при размонтировании также вызывается cleanup.

Функция самого эффекта не должна быть `async`: она возвращает функцию очистки, а не Promise. Асинхронная функция объявляется внутри и вызывается отдельно. Подробнее: [React: useEffect](https://react.dev/reference/react/useEffect).

Для загрузки в этой работе используются зависимости `api`, `q`, `completed`, `priority`, `categoryId` и счётчик обновлений. Значения полей извлекаются из `filters` перед эффектом. Объект API создан в `config.js` вне компонента, поэтому его ссылка не меняется при рендере. Объекты с параметрами запроса создаются внутри эффекта.

`tasks` и `snapshot` не включаются в зависимости загрузки: они являются её результатом. Обновление результата не должно само запускать следующий GET.

### 5.2. Отмена и устаревшие результаты

Один запрос может завершиться позже более нового. Для каждого запуска эффекта требуется собственный `AbortController` и локальный признак актуальности. В cleanup сначала запрос помечается неактуальным, затем отменяется. Перед записью успеха **или ошибки** проверяется актуальность.

Отмена останавливает ожидающий клиентский запрос, но сама по себе не заменяет проверку запоздавшего результата: тестовая или другая реализация API может проигнорировать signal. См. [MDN: AbortController](https://developer.mozilla.org/en-US/docs/Web/API/AbortController).

Для освоения можно рассмотреть абстрактный пример:

```jsx
useEffect(() => {
  let active = true;
  const controller = new AbortController();
  async function run() {
    try {
      const value = await readValue(key, { signal: controller.signal });
      if (active) setValue(value);
    } catch (error) {
      if (active && !controller.signal.aborted) setError(error);
    }
  }
  void run();
  return () => { active = false; controller.abort(); };
}, [key, readValue]);
```

В примере `readValue` должен иметь стабильную ссылку. Это схема жизненного цикла, а не полная реализация хука задания.

### 5.3. StrictMode

В разработке `StrictMode` выполняет дополнительный цикл setup → cleanup → setup. В Network поэтому можно увидеть отменённую пробную загрузку. Отключать StrictMode для сокрытия ошибки не следует. При корректной очистке актуальный запрос завершается нормально.

POST, PATCH и DELETE выполняются в обработчиках пользовательских действий, а не в эффекте первоначальной загрузки. См. [React: StrictMode](https://react.dev/reference/react/StrictMode).

### 5.4. Состояние и служебные ссылки

То, что отображается, хранится в состоянии: статус, снимок данных, ошибки и признак сохранения. `useRef` хранит служебные значения между рендерами без запроса перерисовки: текущий контроллер мутации, признак монтирования.

`setPending(true)` недостаточно для блокировки двух синхронных вызовов: оба могут увидеть прежнее состояние. Ссылка на текущую мутацию устанавливается до первого `await`; повторный вызов сразу возвращает `false`. После завершения ссылка освобождается в `finally`. См. [React: useRef](https://react.dev/reference/react/useRef).

### 5.5. Два независимых результата

Результат изменения и результат последующего GET рассматриваются раздельно:

1. POST/PATCH/DELETE подтвердил успех — изменение выполнено.
2. Запускается новая загрузка списка.
3. Если GET не удался, показывается ошибка обновления и последний успешный снимок.

Ошибка на шаге 3 не превращает шаг 1 в неуспех. Автоматически повторять POST нельзя: это может создать дубликат. Если же ответ на сам POST потерян из-за сетевой ошибки или тайм-аута, клиент не знает, успел ли сервер сохранить запись. Перед ручным повтором следует обновить список.

Отмена запроса изменения при размонтировании тоже не является откатом серверной операции.

## 6. Контракт `useTaskData`

Хук экспортируется из `src/hooks/useTaskData.js`:

```js
useTaskData({ api, filters })
```

### 6.1. Возвращаемые данные

| Поле | Значение |
|---|---|
| `snapshot` | Последний успешный `{ tasks, categories, meta }`. Начальное значение: пустые массивы и `meta: { total: 0 }`. |
| `status` | `'loading'`, `'ready'` или `'error'`. Пустой успешный массив относится к `ready`. |
| `error` | Ошибка загрузки или `null`. |
| `mutationError` | Ошибка операции изменения или `null`. |
| `pending` | Выполняется ли операция изменения. |

В начале загрузки устанавливаются `loading` и `error: null`, старый снимок сохраняется. Успех заменяет снимок целиком и переводит статус в `ready`. Ошибка актуального запроса устанавливает `error`, но не очищает снимок.

Отмена и результат неактуального запроса не меняют пользовательское состояние. `mutationError` не смешивается с `error` и очищается при начале следующей мутации.

### 6.2. Возвращаемые методы

| Метод | Действие |
|---|---|
| `refresh()` | Увеличивает счётчик обновлений, от которого зависит эффект. |
| `saveTask(null, value)` | Вызывает `api.createTask(value, { signal })`. |
| `saveTask(id, value)` | Вызывает `api.updateTask(id, value, { signal })`. |
| `toggleTask(task)` | Вызывает `api.setTaskCompleted(task.id, !task.completed, { signal })`. |
| `deleteTask(id)` | Вызывает `api.deleteTask(id, { signal })`. |
| `resetData()` | Вызывает `api.resetDemoData({ signal })`. |

Все методы изменения возвращают `Promise<boolean>`: `true` только после подтверждённого успеха API, `false` при ошибке, блокировке повторного вызова или размонтировании. Ошибки API перехватываются внутри хука. Введённый `value` уже нормализован формой; сервер повторно проверяет поля.

После успешной мутации увеличивается счётчик обновлений. Новый GET выполняется эффектом с **актуальными** фильтрами, а не с фильтрами, захваченными в момент начала сохранения. Локально дописывать задачи в снимок или назначать id не требуется.

### 6.3. Способ загрузки для этой работы

Каждый цикл загрузки вызывает:

```js
api.loadInitialData({ q, completed, priority, categoryId }, { signal })
```

Метод параллельно запрашивает задачи и категории и возвращает общий снимок. Повторная загрузка небольшого справочника выбрана для простого согласованного контракта. Кэширование категорий не входит в обязательную часть. Именно этот метод используется подставным API в тестах.

Для мутации создаётся отдельный контроллер. Смена фильтров отменяет только чтение, а размонтирование отменяет чтение и текущую мутацию. Служебный эффект монтирования восстанавливает признак активности в setup, чтобы корректно работать в StrictMode.

Добавить импорты `useEffect`, `useRef`, счётчик `revision` и эффект загрузки. Начать с успешного ответа и состояния ошибки. Убедиться, что первоначально появляются задачи и категории, а пустой ответ не считается ошибкой.

### Шаг 3. Реализовать очистку и повтор

Добавить контроллер и признак актуальности каждого эффекта. В cleanup отменять запрос и запрещать запись его результатов. Защита применяется к обеим веткам — успеху и ошибке.

`refresh()` увеличивает `revision` через функциональное обновление. Повтор работает и после ошибки самого первого запроса, когда категории ещё не получены.

### Шаг 4. Реализовать общую функцию мутации

Во внутреннюю `mutate(operation)` вынести:

1. проверку монтирования и блокировки;
2. создание контроллера и немедленное сохранение его в ref;
3. установку `pending: true`, очистку `mutationError`;
4. ожидание вызова API;
5. проверку актуальности после ожидания;
6. увеличение `revision` при успехе и возврат `true`;
7. сохранение ошибки при неуспехе и возврат `false`;
8. освобождение блокировки в `finally`.

Освобождать следует только контроллер своей операции: завершение старого вызова не должно затереть ссылку нового. После размонтирования обновлять React-состояние и запускать новый GET не следует.

Поверх общей функции реализовать методы из раздела 6. Подтверждение удаления находится в `App`, до вызова хука.

### Шаг 5. Проверить асинхронную форму

В готовой `TaskForm` уже используется `await onSave(value)` и локальная защита от повторной отправки. Необходимо разобрать этот код и объяснить разницу с ПР7.

Если используется собственная форма, обеспечить те же правила:

- до запроса проверяются поля;
- при `false` черновик сохраняется;
- только при `true` форма очищается или выходит из режима редактирования;
- при `pending` поля и изменяющие кнопки заблокированы;
- неверные поля имеют связанные сообщения и `aria-invalid`;
- ошибки сервера доступны пользователю, а не только Console.

Пока идёт загрузка или показана ошибка GET, изменяющие элементы в готовом интерфейсе отключены: показанные карточки могут быть устаревшими. Фильтры и кнопка обновления доступны. После восстановления GET форма снова становится доступной.

### Шаг 6. Проверить редактирование при фильтрации

`App` хранит снимок редактируемой записи для формы. Поэтому смена фильтра не стирает незавершённый черновик, даже если карточка исчезла из выборки. Это отличается от поиска редактируемой записи только в текущем массиве.

При PATCH из формы отправляются только название, приоритет и категория: сохранённый в черновике статус не должен перезаписать актуальный серверный `completed`. При удалении редактируемой записи форма возвращается к созданию. При удалении записи из другой вкладки серверный 404 показывается как ошибка изменения.

## 10. Типичные ошибки

| Проявление | Причина и исправление |
|---|---|
| Бесконечная загрузка запросами | Новый объект api в каждом рендере или результат запроса в зависимостях эффекта. |
| Эффект возвращает Promise | `async` указан у callback `useEffect`; перенести асинхронную функцию внутрь. |
| Старый фильтр заменяет новый | Нет признака актуальности; отмены недостаточно. |
| После быстрой смены фильтра появляется ошибка отмены | `aborted` выводится как пользовательская ошибка. |
| Две записи после двойного нажатия | Блокировка только через state; нужен немедленный ref до `await`. |
| Создание произошло, но форма предлагает повторить | Ошибка повторного GET смешана с результатом POST. |
| При смене фильтра пропадает сохранение | Для чтения и мутации используется общий контроллер. |
| После ошибки GET нельзя восстановить категории | Повтор загружает только задачи, хотя первая загрузка не удалась. |
| После удаления ошибка JSON | Клиент пытается разобрать тело ответа 204. |
| В preview запрос уходит к серверу Vite | Использован относительный `/api` без соответствующего proxy; в заготовке нужен абсолютный адрес. |
| Новый `.env` не влияет на приложение | Не перезапущен dev-сервер или не пересобран `dist`. |
| В отчёте указан общий размер системы | `meta.total` описывает только отфильтрованную выборку. |
