**Тема: Реализация операций изменения данных и интеграция с клиентом**

**Дисциплина:** Технологии индустриального программирования<br>

**Результат:** React-клиент, работающий с собственным Express API; создание, редактирование, изменение статуса и удаление задач в памяти сервера<br>
[К описанию курса](../../README.md) · [ПР9](../practice-09/README.md) · [ПР11](../practice-11/README.md) · [React-клиент ПР8](../practice-08/README.md) · [Стартовые файлы](./starter/)

> ПР9 реализовала операции чтения собственного API. В ПР10 необходимо добавить операции записи, проверить данные на сервере и подключить выполненный React-клиент ПР8. Форматы задач, категорий, фильтров и ответов сохраняются. Постоянное хранение в PostgreSQL относится к ПР11–ПР12.

## 1. Цель и результат

**Цель работы** — связать клиентские действия с серверными изменениями данных, сохранив согласованный HTTP-контракт и корректную обработку ошибок.

После выполнения:

- POST создаёт задачу с назначенными сервером id и статусом;
- PATCH меняет только переданные поля;
- DELETE удаляет запись и возвращает ответ без тела;
- сервер проверяет типы, значения, обязательные и неизвестные поля;
- неверный запрос не изменяет хранилище и не расходует id;
- React получает актуальный список после успешной записи;
- ошибка записи сохраняет черновик формы и снимает блокировку;
- обновление страницы сохраняет записи, пока работает тот же сервер;
- перезапуск процесса или учебный reset восстанавливает исходные данные;
- автоматические проверки и ручной клиентский протокол выполнены и отражены в отчёте.

Это учебное приложение без базы данных и авторизации. Пароли, реальные персональные данные, публикация API в интернете, Docker и загрузка файлов в обязательный объём не входят.

## 4. Контракт операций записи

Операции GET и фильтры сохраняют [контракт ПР9](../practice-09/README.md#4-контракт-api). Query-параметры записи в этой работе не используются и не меняют действие маршрута.

### 4.1. Создание

```http
POST /api/tasks
Content-Type: application/json

{"title":"Подготовить защиту","priority":"high","categoryId":2}
```

Успешный ответ — **201 Created**, заголовок `Location: /api/tasks/35` и тело:

```json
{"data":{"id":35,"title":"Подготовить защиту","completed":false,"priority":"high","categoryId":2}}
```

Id 35 получается только для первой созданной записи исходного набора после запуска/reset. Следующие id увеличиваются на единицу. `id` и `completed` задаются сервером: попытка передать любое из этих полей при POST отклоняется, даже если значение совпадает с ожидаемым.

### 4.2. Частичное обновление

```http
PATCH /api/tasks/4
Content-Type: application/json

{"completed":true}
```

Успешный ответ — **200 OK**, `{ data: updatedTask }`. PATCH принимает любое непустое подмножество `title`, `priority`, `categoryId`, `completed`. Непереданные поля сохраняются. `id` менять нельзя.

При сохранении формы клиент ПР8 передаёт `title`, `priority`, `categoryId`; при переключении статуса — только `completed`. Редактирование названия выполненной задачи не должно сбрасывать её статус.

### 4.3. Удаление

```http
DELETE /api/tasks/4
```

Успех — **204 No Content**, без JSON и без тела. Повторное удаление той же записи возвращает **404 TASK_NOT_FOUND**. После удаления нельзя уменьшать счётчик id или использовать длину массива в качестве следующего id.

### 4.4. Валидация

| Поле | POST | PATCH | Правило |
|---|---|---|---|
| `title` | Обязательно | Если передано | Строка, после `trim` от 1 до 100 единиц `length` JavaScript-строки. |
| `priority` | Обязательно | Если передано | Строго `low`, `medium`, `high`. |
| `categoryId` | Обязательно | Если передано | Положительное безопасное целое **число**, существующее среди категорий. |
| `completed` | Запрещено | Если передано | Только boolean, включая `false`. |
| `id` | Запрещено | Запрещено | Назначается сервером и не меняется. |
| Другие поля | Запрещены | Запрещены | Ошибка по каждому неизвестному имени. |

Тело должно быть JSON-объектом, а не массивом, строкой, числом, boolean или `null`. Пустой объект PATCH запрещён. Преобразовывать `'2'` в категорию 2 и `'false'` в boolean на сервере не следует: это нарушения контракта тела JSON. В query ПР9 значения были строками; тело JSON уже поддерживает собственные типы.

Все обнаруженные ошибки полей собираются в `details` одного ответа:

```json
{"error":{"code":"VALIDATION_ERROR","message":"Данные не прошли проверку.","details":{"title":"Название обязательно.","categoryId":"Неизвестная категория."}}}
```

Точные тексты сообщений могут отличаться; статус, код и имена неверных полей фиксированы. Для неверного типа всего тела используется ключ `body`. Если PATCH содержит одновременно корректное название и неверную категорию, **не применяется ни одно изменение**.

### 4.5. Разбор тела и ошибки

| Ситуация | Статус | Код |
|---|---:|---|
| Неверные поля или тип JSON-значения | 400 | `VALIDATION_ERROR` |
| Повреждённый JSON или пустое тело POST/PATCH | 400 | `INVALID_JSON` |
| Неверный id | 400 | `INVALID_ID` |
| Корректный id отсутствует | 404 | `TASK_NOT_FOUND`, `details: { id }` |
| Метод не поддерживается данным маршрутом | 405 | `METHOD_NOT_ALLOWED`, заголовок `Allow` |
| Тело превышает 16 КиБ | 413 | `PAYLOAD_TOO_LARGE` |
| Нет `Content-Type: application/json`, неподдерживаемая кодировка или сжатие | 415 | `UNSUPPORTED_MEDIA_TYPE` |
| Неожиданное исключение | 500 | `INTERNAL_ERROR` |

Для локальных запросов используется UTF-8; `application/json; charset=utf-8` допустим. Лимит 16 КиБ относится к байтам тела запроса, ограничение названия 100 — к длине строки JavaScript. Это разные проверки.

JSON middleware подключён только к POST задач и PATCH. Он не должен перехватывать OPTIONS, DELETE и учебный reset без тела. В PATCH сначала проверяется id и существование записи, затем тело: `/api/tasks/4abc` без JSON возвращает 400 INVALID_ID, `/api/tasks/2` — 404 TASK_NOT_FOUND.

После получения тела запись могла уже быть удалена другим запросом. Поэтому результат `store.updateTask` проверяется повторно: `null` означает 404, а не `200 { data: null }`.

### 4.6. Методы, CORS и учебный reset

| Путь | Значение `Allow` при 405 |
|---|---|
| `/api/health`, `/api/categories` | `GET, HEAD, OPTIONS` |
| `/api/tasks` | `GET, HEAD, POST, OPTIONS` |
| `/api/tasks/:id` | `GET, HEAD, PATCH, DELETE, OPTIONS` |
| `/api/debug/reset` | `POST, OPTIONS` |

OPTIONS по-прежнему возвращает 204 до маршрутов. CORS допускает GET, HEAD, POST, PATCH, DELETE, OPTIONS и заголовки Accept, Content-Type. `Access-Control-Expose-Headers: Location` позволяет браузерному коду прочитать Location.

Предоставленный `POST /api/debug/reset` без тела возвращает `{ data: { reset: true, total: 12 } }`. Он сохраняет работу кнопки сброса в клиенте ПР8. Это учебная операция только для локального сервера, слушающего `127.0.0.1`; запускать её следует после завершения текущих операций записи. Остальные `/api/debug/*` из ПР8 не реализуются и не нужны основным сценариям интерфейса.

## 5. Теория

### 5.1. Где должна выполняться валидация

Проверка формы помогает быстро сообщить об ошибке, но сервер нельзя считать защищённым её наличием. Запрос может прийти из другого клиента, скрипта или DevTools. Поэтому сервер независимо проверяет типы, поля и существование категории.

Порядок обработки: разобрать тело → проверить все поля → получить нормализованный объект → изменить хранилище → отправить ответ. Нельзя сначала присвоить название, затем обнаружить неверную категорию и вернуть 400: данные уже будут частично изменены.

### 5.2. JSON middleware

Предоставленный `express.json` читает тело и помещает результат в `req.body`. Настройки заготовки: ограничение 16 КиБ, `strict: false`, `inflate: false`. Режим `strict: false` позволяет отдельно различать синтаксически корректный JSON `null` или `42` и ошибочный предметный формат: такие значения затем отклоняет `validateTaskInput`.

Парсер не проверяет существование категории и длину названия. Его ошибки преобразуются в наш JSON-контракт через `errorHandler`. Пустое тело выделено отдельно; внутренний текст ошибки парсера и исходный запрос клиенту не отправляются. Подробнее: [Express: body-parser](https://expressjs.com/en/resources/middleware/body-parser.html).

### 5.3. POST и PATCH

POST создаёт новый ресурс. PATCH описывает изменение существующего: отсутствие поля означает «сохранить прежнее значение», а не «присвоить значение по умолчанию».

```js
const book = { id: 7, title: 'Алгоритмы', available: true };
const changes = { title: 'Новое название' };
const updated = { ...book, ...changes, id: book.id };
```

В примере `available` сохраняется. Такое объединение допустимо только после проверки разрешённых полей `changes`. Полный пример запускается командой `npm run example`.

Наличие поля проверяется через `Object.hasOwn(value, 'completed')`. Условие `if (value.completed)` не подходит: оно пропустит корректное значение `false`.

### 5.4. Id и память процесса

При запуске `nextId` равен максимальному исходному id плюс один: 35. При успешном создании он увеличивается. Удаление не меняет счётчик. Ошибочная валидация не должна вызывать метод создания.

В пределах этого процесса изменения массива и счётчика выполняются синхронно без `await`, поэтому создание одной записи завершается до выполнения следующего обработчика записи. Это не заменяет транзакции и уникальные ограничения при переходе к базе данных или нескольким процессам.

Хранилище возвращает копии записей: изменение результата `getTask` не должно незаметно менять серверные данные. Сама память процесса не является постоянным хранилищем. Перезагрузка браузера и перезапуск сервера дают разные результаты.

### 5.5. Неизвестные поля

Входной объект нельзя без проверки объединять с записью хранилища. Иначе клиент сможет передать `id` или другие неразрешённые поля. Валидатор формирует **новый объект** только из проверенных полей.

Имена ошибок также приходят из внешнего ввода. Для словаря `details` удобно использовать `Object.create(null)`, чтобы имя `__proto__` сохранялось как обычный ключ. Проверка перебирает собственные ключи через `Object.keys`, а наличие проверяется через `Object.hasOwn`.

### 5.6. Изменение и последующая загрузка — разные операции

После успешного POST/PATCH/DELETE клиент ПР8 повторно загружает список с текущими фильтрами. Отдельная ошибка GET после успешного POST не означает, что создание не произошло. Автоматически повторять POST нельзя: можно создать дубликат.

Если ответ на сам POST потерян, клиент не всегда может определить, было ли изменение выполнено. Необходимо показать ошибку и проверить актуальный список. Автоматические повторы записи, оптимистические обновления и механизм идемпотентных ключей в обязательную часть этой работы не входят.

## 6. Последовательность выполнения

### Шаг 1. Запустить чтение

Установить зависимости, выполнить health, GET категорий и списка, затем `npm run check:read`. Этот набор должен проходить до реализации записи. Разобрать разделение между `routes.js`, `write-routes.js`, хранилищем и валидатором.

### Шаг 2. Реализовать validateTaskInput

Сигнатура:

```js
validateTaskInput(value, { partial = false, categoryIds })
```

`categoryIds` — Set идентификаторов существующих категорий. Функция:

1. Проверяет, что тело является объектом нужного вида.
2. Определяет разрешённые и обязательные поля для POST/PATCH.
3. Собирает неизвестные имена и все ошибки полей.
4. Обрезает пробелы названия и формирует новый объект только из переданных разрешённых полей.
5. При ошибках выбрасывает `ApiError(400, 'VALIDATION_ERROR', message, details)`.
6. При успехе возвращает нормализованный объект, не изменяя входной.

Для PATCH не следует автоматически добавлять `completed:false`, пустое название или категорию по умолчанию. Валидатор не обращается к `req`, `res` и глобальному массиву.

### Шаг 3. Реализовать методы хранилища

| Метод | Результат |
|---|---|
| `createTask(value)` | Добавляет запись с серверными id и `completed:false`; возвращает копию. |
| `updateTask(id, changes)` | Применяет проверенные поля; возвращает копию либо `null`, если записи нет. |
| `deleteTask(id)` | Удаляет одну найденную запись; возвращает `true` либо `false`. |

Методы принимают уже проверенные значения. В create необходимо явно собрать поля новой записи, а в update сохранить исходный id. Массив нельзя перезаписывать результатом фильтрации интерфейса: фильтры влияют на чтение, а не на содержимое хранилища.

### Шаг 4. Реализовать маршруты

Для POST получить Set категорий из `store.listCategories()`, проверить `req.body`, вызвать `store.createTask`. Отправить Location и 201 с `{ data: task }`.

Для PATCH использовать `partial:true` и `req.task.id`, установленный `requireTask`. Вызвать `store.updateTask`; для `null` вернуть 404 TASK_NOT_FOUND с `details.id`, для записи — 200 и JSON.

Для DELETE вызвать `store.deleteTask`; для `false` вернуть 404 TASK_NOT_FOUND, для успеха — `res.status(204).end()`. Дополнительный JSON в эту ветвь не добавляется.

Предоставленные обработчики 405 уже стоят после регистрации методов. Общие ошибки передаются финальному `errorHandler`; не следует заменять их HTML-страницами или сообщениями только в Console.

### 8.2. Запросы напрямую

Создать временный `task.json` с содержимым:

```json
{"title":"Проверить сервер","priority":"high","categoryId":2}
```

Файл сохранить в UTF-8 без BOM. При работающем сервере выполнить из папки с файлом:

```bash
curl -i -X POST "http://127.0.0.1:5505/api/tasks" -H "Content-Type: application/json" --data-binary "@task.json"
```

В Windows PowerShell вместо `curl` использовать `curl.exe`. Передача файла позволяет избежать различий экранирования JSON в оболочках. Id взять из фактического ответа, не подставлять 35 вслепую.

Создать `patch.json` с `{"completed":true}`, затем выполнить запрос для фактического id, например 35:

```bash
curl -i -X PATCH "http://127.0.0.1:5505/api/tasks/35" -H "Content-Type: application/json" --data-binary "@patch.json"
curl -i -X DELETE "http://127.0.0.1:5505/api/tasks/35"
```

Для отрицательного сценария заменить в `task.json` категорию на `999` или название на пробелы. Ожидается 400 VALIDATION_ERROR. Проверить список до и после запроса. Временные файлы необязательно включать в репозиторий.

## 9. Типичные ошибки

| Проявление | Причина и исправление |
|---|---|
| Запись работает, но через прежний API | Запущена команда `npm run api` в ПР8; остановить её и проверить адрес/процесс. |
| После PATCH потерялись поля | PATCH реализован как полная замена или валидатор добавляет значения по умолчанию. |
| Нельзя вернуть задачу в работу | Проверяется truthy вместо наличия `completed`. |
| После ошибки изменилось название | Хранилище обновлено до окончания всей валидации. |
| После удаления повторяется id | Используется длина массива или уменьшается счётчик. |
| DELETE показывает ошибку JSON | Сервер отправляет лишнее тело либо клиент разбирает 204 как JSON. |
| Категория `'2'` принимается как 2 | В JSON нарушенные типы незаметно приводятся вместо отклонения. |
| JSON-ошибка возвращается как HTML | Ошибка парсера не прошла через финальный JSON middleware. |
| POST работает в терминале, но не в браузере | Проверить OPTIONS, разрешённые методы/заголовки и адрес API. |
| После успешного создания возникла вторая запись | Ошибка повторного GET вызвала повторный POST. |
| PATCH вернул data:null | Запись удалена во время чтения тела; нужен повторный контроль результата updateTask. |
| Новый `.env` не влияет на preview | Пересобрать клиент после изменения адреса. |
