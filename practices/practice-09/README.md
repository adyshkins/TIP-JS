# Практическая работа № 9

**Тема: Создание собственного HTTP API**

**Дисциплина:** Технологии индустриального программирования<br>
**Трек:** фулстек-разработка на JavaScript<br>
**Форма выполнения:** индивидуальная<br>
**Результат:** собственный Express-сервер с операциями чтения задач и категорий, фильтрацией и единым форматом ошибок<br>
[К описанию курса](../../README.md) · [ПР8](../practice-08/README.md) · [ПР10](../practice-10/README.md) · [Контракт ПР6](../practice-06/README.md#4-контракт-учебного-api) · [Стартовые файлы](./starter/)

> В ПР6 и ПР8 использовался готовый учебный сервер. В ПР9 необходимо самостоятельно реализовать часть его контракта на Node.js и Express. Внешний формат данных сохраняется. Создание, редактирование, удаление задач и полная интеграция с React относятся к ПР10.

## 1. Цель и результат

**Цель работы** — разобраться, как сервер принимает HTTP-запрос, выбирает обработчик, проверяет параметры, получает данные и формирует ответ.

После выполнения сервер:

- возвращает состояние сервиса, категории, список задач и отдельную задачу;
- фильтрует задачи по статусу, приоритету, категории и тексту;
- отклоняет некорректные, повторяющиеся и неизвестные параметры списка;
- различает неверный идентификатор, отсутствующую запись и неизвестный маршрут;
- возвращает JSON с согласованными статусами и кодами ошибок;
- обрабатывает HEAD и OPTIONS и возвращает CORS-заголовки;
- сохраняет исходные данные при любых операциях чтения;
- проходит модульные и HTTP-проверки.

Данные хранятся в памяти процесса. PostgreSQL, авторизация, загрузка файлов, операции записи, Docker и публикация в интернете в обязательную часть не входят. Диагностические маршруты `/api/debug/*` из учебного сервера здесь не реализуются.

## 2. Подготовка и объём

Необходимы знания функций, массивов, объектов, ES-модулей, Promise, HTTP-методов, статусов и JSON. Из ПР8 используется понимание клиентского контракта; перенос интерфейса в серверный проект не требуется.

**Предлагаемый формат:** одна аудиторная пара 90 минут после предварительного чтения, с самостоятельным завершением варианта, проверок и отчёта.

| Этап | Ориентир | Содержание |
|---|---:|---|
| Подготовка | 10 минут | Установка, запуск, health-запрос. |
| Базовые маршруты | 15 минут | Категории и список без фильтров. |
| Параметры и логика | 25 минут | Разбор фильтров, поиск, отдельная задача. |
| Ошибки и методы | 20 минут | 400, 404, 405; порядок обработчиков. |
| Проверка | 20 минут | HTTP-запросы, тесты и вариант. |

В заготовке предоставлены исходные данные ПР8, фабрика приложения, запуск, инфраструктура ошибок и CORS, хранилище, пример и проверки. **Реализовать необходимо `validation.js`, `task-service.js` и `routes.js`.** Не следует заменять их готовым сервером ПР8 на `node:http`: задача работы — освоить Express и разделение ответственности.

## 4. Контракт API

### 4.1. Маршруты чтения

| Метод и путь | Статус | Тело |
|---|---:|---|
| `GET /api/health` | 200 | `{ data: { status: "ok" } }` |
| `GET /api/categories` | 200 | `{ data: category[], meta: { total } }` |
| `GET /api/tasks` | 200 | `{ data: task[], meta: { total, filters } }` |
| `GET /api/tasks/:id` | 200 | `{ data: task }` |
| `HEAD` для тех же путей | Как у GET | Без тела. |
| `OPTIONS` для любого пути | 204 | Без тела, CORS-заголовки. |

```js
// Категория
{ id: 2, name: 'Проект' }
// Задача
{ id: 4, title: 'Подготовить модель задач', completed: false, priority: 'high', categoryId: 2 }
```

Идентификаторы задач разреженные: 1, 4, 7, …, 34. Обращение к задаче с id 4 не означает обращение к элементу массива с индексом 4. Порядок записей сохраняется как в исходном наборе.

`meta.total` — размер **полученной выборки**, а не всего хранилища. Без фильтров он равен 12. Список категорий содержит три записи. При отсутствии совпадений возвращается **200 и `data: []`**, а не 404.

### 4.2. Query-параметры списка

| Параметр | Допустимые значения | Значение без параметра |
|---|---|---|
| `completed` | Строго строки `true` или `false`; преобразуются в boolean. | `null` |
| `priority` | `low`, `medium`, `high`, с учётом регистра. | `null` |
| `categoryId` | Запись положительного безопасного целого без ведущих нулей. | `null` |
| `q` | Строка после `trim`, не длиннее 100 единиц `length` JavaScript-строки. | `""` |

Значения `completed=`, `priority=`, `categoryId=` неверны. Значение `q=` допустимо и не ограничивает выборку. Неизвестные имена параметров и повторения любого разрешённого имени отклоняются, даже если значения одинаковы. Имена параметров чувствительны к регистру.

Пример:

```text
GET /api/tasks?completed=false&priority=high&categoryId=2
```

Возвращаются задачи **4 и 34**, `meta.total: 2`, а `meta.filters` имеет вид:

```json
{ "completed": false, "priority": "high", "categoryId": 2, "q": "" }
```

Все условия объединяются через **И**. Поиск выполняется по вхождению текста в `title` без учёта регистра; для обеих строк используется `toLocaleLowerCase('ru-RU')`. Поиск `ПРОВЕР` на исходном наборе возвращает задачи 7 и 16.

Корректный, но отсутствующий `categoryId=999` возвращает пустую выборку. Валидация существования категории при **записи** относится к ПР10. Query-параметры проверяются только у списка задач; health, категории и отдельная задача в этой работе их игнорируют, как соответствующие GET-маршруты учебного API.

### 4.3. Идентификаторы

Функция `parsePositiveId(raw)` принимает строку, которая должна соответствовать `/^[1-9]\d*$/`. После преобразования требуется `Number.isSafeInteger(value)`. Результат — число или `null`, а не исключение.

Недопустимы `0`, `-1`, `01`, `1.5`, `1e2`, `4abc`, пробелы и числа за пределами безопасных целых. Одного `parseInt` недостаточно: он принимает начало строки `4abc` как число 4.

Express уже декодирует `req.params.id`. Повторный `decodeURIComponent` не нужен. Ошибка кодирования, например `%ZZ`, обрабатывается предоставленным middleware как `400 INVALID_ID`.

### 4.4. Ошибки и неподдерживаемые методы

```json
{ "error": { "code": "TASK_NOT_FOUND", "message": "Задача не найдена.", "details": { "id": 2 } } }
```

| Условие | Статус | `error.code` |
|---|---:|---|
| Неверный query списка | 400 | `INVALID_QUERY` |
| Неверный id задачи | 400 | `INVALID_ID` |
| Корректный id отсутствует | 404 | `TASK_NOT_FOUND` |
| Неизвестный путь | 404 | `ROUTE_NOT_FOUND` |
| Изменяющий/другой метод на известном пути | 405 | `METHOD_NOT_ALLOWED` |
| Неожиданное исключение | 500 | `INTERNAL_ERROR` |

Код ошибки и статус фиксированы. Текст `message` может отличаться, но должен быть непустым и понятным. Для `TASK_NOT_FOUND` обязательно `details: { id }`; для остальных ошибок `details` необязателен. Стек исключения и внутренние данные не отправляются клиенту.

В ПР9 у четырёх известных путей разрешены только GET, HEAD и OPTIONS. Остальные методы возвращают 405 и `Allow: GET, HEAD, OPTIONS`. Это промежуточный контракт: в ПР10 список методов расширяется. Для таких неподдерживаемых методов проверка существования задачи не требуется; например, `DELETE /api/tasks/999` также возвращает 405. OPTIONS обрабатывается раньше маршрутов, в том числе для неизвестного пути. Остальные запросы к неизвестным путям получают 404.

JSON-ответы, включая ошибки, содержат `Content-Type: application/json; charset=utf-8`, `Cache-Control: no-store` и CORS-заголовки. Эти общие настройки уже предоставлены. Для 204 и HEAD тело отсутствует.

## 5. Теория

### 5.1. Node.js и Express

Node.js исполняет JavaScript вне браузера. Здесь нет DOM, `window` и `localStorage`. Express связывает HTTP-метод и путь с функцией обработчика. Query-строка не является частью пути маршрута: `/tasks?q=API` обрабатывается маршрутом `/tasks`.

`req` описывает запрос, `res` формирует ответ. `res.status(200).json(value)` устанавливает статус и отправляет JSON. После отправки не следует продолжать ветвление и пытаться отправить второй ответ. Удобно завершать ветви через `return`.

Небольшой независимый пример находится в `examples/books.js`:

```bash
npm run example
```

Адрес: http://127.0.0.1:5510/books/3. Для `/books/9` возвращается 404. Пример не реализует полный контракт задания. Подробнее: [Express: Routing](https://expressjs.com/en/guide/routing.html).

### 5.2. Параметры пути и запроса

`req.params.id` получается из маршрута `/tasks/:id`. Для списка в этой работе используется:

```js
const url = new URL(req.originalUrl, 'http://localhost');
const searchParams = url.searchParams;
```

Базовый адрес нужен только для разбора относительного URL, сетевой запрос здесь не выполняется. `searchParams.getAll(name)` позволяет обнаружить повторения. Превращать параметры в обычный объект до этой проверки не следует: так можно потерять сведения о дубликатах.

Любые данные запроса считаются внешним вводом. `Boolean('false')` равно `true`, поэтому преобразование статуса выполняется только после проверки допустимых строк: `raw === 'true'`.

### 5.3. Middleware и порядок

Обработчики выполняются в порядке регистрации. Обычный middleware имеет параметры `(req, res, next)`. Вызов `next()` передаёт управление следующему, отправка ответа завершает обработку в текущей ветви.

Порядок в приложении:

1. Общие заголовки и ранний ответ OPTIONS.
2. Router с GET-маршрутами.
3. Внутри Router — обработчики 405 для известных путей, зарегистрированные **после** GET.
4. Обработчик неизвестного маршрута 404.
5. Обработчик ошибок `(error, req, res, next)`.

Если 404 зарегистрирован раньше Router, до маршрутов управление не дойдёт. Если `router.all('/tasks', ...)` стоит до GET, он перехватит и чтение.

### 5.4. Исключения и HTTP-ошибки

`ApiError` хранит статус, код, сообщение и необязательные детали. Например, неверный фильтр порождает `new ApiError(400, 'INVALID_QUERY', 'Некорректный статус.')`. Синхронное исключение внутри обработчика Express передаёт обработчику ошибок. Для будущего асинхронного кода в Express 5 отклонённый Promise возвращённого обработчиком результата также передаётся обработчику ошибок. Подробнее: [Express: Error Handling](https://expressjs.com/en/guide/error-handling.html).

Ожидаемая ошибка пользователя не должна превращаться в 500. При этом нельзя объявлять любое исключение `TypeError` ошибкой запроса: оно может возникнуть из-за дефекта серверного кода. В заготовке ожидаемые ошибки явно представлены классом `ApiError`.

### 5.5. Разделение ответственности

| Модуль | Отвечает за | Не должен делать |
|---|---|---|
| `validation.js` | Преобразование строк и проверку параметров. | Читать `req`, отправлять `res`. |
| `task-service.js` | Выборку и поиск в переданном массиве. | Знать HTTP-статусы, запускать сервер. |
| `store.js` | Данные конкретного приложения. | Формировать HTTP-ответ. |
| `routes.js` | Связь HTTP с логикой и форматом контракта. | Хранить глобальный массив задач. |
| `app.js` | Сборку middleware и Router. | Открывать порт при импорте. |
| `server.js` | Порт и запуск приложения. | Реализовывать фильтры. |

`createApp()` возвращает новое приложение. Это позволяет тестам открыть сервер на свободном порту и закрыть его после проверок. Не нужно мокировать весь HTTP-слой или обращаться к запущенному вручную серверу.

### 5.6. CORS и клиент ПР8

Учебный API допускает чтение из другого origin через `Access-Control-Allow-Origin: *`. Такой режим используется только для этого локального API без учётных данных. CORS — правило доступа браузерного JavaScript к ответу, а не авторизация и не запрет прямых HTTP-запросов.

В ПР9 собственный сервер можно использовать для чтения из выполненной ПР8. Создание, редактирование и удаление пока получат 405. Это ожидаемая граница этапа, а не готовая полная замена сервера ПР8. Для обязательной проверки ПР9 достаточно запросов и автоматических тестов; полный клиентский прогон относится к ПР10.

## 6. Задание и последовательность выполнения

### Шаг 1. Проверить окружение

Установить зависимости, запустить сервер и выполнить health-запрос. Убедиться, что процесс принадлежит ПР9. Изучить порядок подключения middleware в `app.js` и поведение `ApiError`. Отдельно запустить пример с книгами и остановить его.

### Шаг 2. Реализовать категории и список без фильтров

В `routes.js` получить категории через `store.listCategories()` и вернуть `data` с `meta.total`. Для списка подготовить вызов `store.listTasks(filters)`. Не импортировать `data.js` прямо в маршруты: источником данных является переданный `store`.

Фильтры по умолчанию: `{ completed: null, priority: null, categoryId: null, q: '' }`. Реализовать `selectTasks`, сначала проверив отсутствие ограничений, затем каждое условие. Функция работает с переданными данными и не изменяет их.

### Шаг 3. Реализовать валидацию

В `validation.js` реализовать `parsePositiveId` и `parseFilters` по разделу 4. Рекомендуемый порядок для фильтров:

1. Проверить имена всех параметров.
2. Убедиться, что каждое имя встречается не более одного раза.
3. Проверить и преобразовать значения.
4. Вернуть новый объект со всеми четырьмя полями.

При ошибке выбросить `ApiError` с кодом `INVALID_QUERY`. Отсутствие параметра и явно переданное пустое значение различаются. `q` сначала обрезается по краям, затем проверяется его длина.

### Шаг 4. Реализовать фильтрованный список

В обработчике `/tasks` разобрать `req.originalUrl`, передать `searchParams` в `parseFilters`, затем вызвать `store.listTasks(filters)`. Ответ содержит `data` и `meta: { total: data.length, filters }`.

Проверить отдельно `completed=false`, поиск по кириллице и комбинацию трёх фильтров. Не следует применять `if (filters.completed)`: это пропускает значение `false`. Отсутствие ограничения обозначается именно `null`.

### Шаг 5. Реализовать отдельную задачу

В `findTask(tasks, id)` найти запись по полю `id`; при отсутствии вернуть `null`. В `/tasks/:id` выполнить по порядку:

1. Преобразовать строку `req.params.id` через `parsePositiveId`.
2. Для `null` выбросить `400 INVALID_ID`.
3. Получить запись через `store.getTask(id)`.
4. Для отсутствующей записи выбросить `404 TASK_NOT_FOUND` с `{ id }`.
5. Отправить `200` и `{ data: task }`.

### Шаг 6. Добавить 405

После GET-маршрутов зарегистрировать `router.all` для `/health`, `/categories`, `/tasks` и `/tasks/:id`. Установить `Allow: GET, HEAD, OPTIONS` и передать `ApiError(405, 'METHOD_NOT_ALLOWED', ...)` обработчику ошибок. Маршруты GET уже обеспечивают ответы на HEAD, если отдельный обработчик HEAD не переопределён.

## 8. Проверки

### 8.1. Автоматические

Из `practice-09`:


Модульные тесты проверяют разбор параметров, границы чисел и строк, фильтры, отсутствие мутации и работу с другим массивом. HTTP-тесты обращаются к настоящему локальному Express-серверу: проверяют статусы, JSON, фильтры, HEAD, OPTIONS, Allow и общие заголовки. Проверки не открывают браузер и не подтверждают работу браузерного CORS. Они также не заменяют защиту и объяснение кода. Исходная заготовка намеренно не проходит все тесты: `NOT_IMPLEMENTED` требуется заменить собственной реализацией. Успешный health-запрос сам по себе не подтверждает выполнение задания.

### 8.2. Ручные HTTP-запросы

При работающем сервере открыть второй терминал. В Windows PowerShell используется именно `curl.exe`; в macOS/Linux — `curl`.

```bash
curl -i "http://127.0.0.1:5505/api/tasks?completed=false&priority=high&categoryId=2"
curl -i "http://127.0.0.1:5505/api/tasks/4"
curl -i "http://127.0.0.1:5505/api/tasks/2"
curl -i "http://127.0.0.1:5505/api/tasks/4abc"
curl -i "http://127.0.0.1:5505/api/tasks?q=a&q=b"
curl -i -X POST "http://127.0.0.1:5505/api/tasks"
curl -I "http://127.0.0.1:5505/api/tasks"
curl -i -X OPTIONS "http://127.0.0.1:5505/api/tasks"
```

URL с `&` обязательно заключать в кавычки. `-i` показывает статус и заголовки вместе с телом, `-I` выполняет HEAD. Строки JSON могут отображаться без форматирования — это не ошибка.

## 9. Типичные ошибки

| Проявление | Причина и исправление |
|---|---|
| `completed=false` возвращает выполненные задачи | Применён Boolean к строке; нужна явная проверка. |
| id 4 возвращает другую задачу | Использован индекс массива вместо поиска по id. |
| `4abc` принимается как id | Использован только parseInt без проверки всей строки. |
| Пустой результат даёт 404 | Список не найденных совпадений перепутан с отсутствующим ресурсом. |
| Повторяющийся query принимается | Потеряны дубликаты при преобразовании в объект. |
| После фильтрации общий список уменьшился | Изменён массив хранилища вместо создания выборки. |
| Все запросы возвращают 404/405 | Неверный порядок middleware. |
| Ошибка возвращается как HTML | Обработчик ошибок не подключён последним или имеет неверную сигнатуру. |
| `Cannot set headers after they are sent` | Выполняется вторая отправка ответа; завершить ветвь. |
| Тесты зависают после завершения | Сервер запускается при импорте app.js либо не закрывается. |
| После изменений работает старое поведение | Запущен API предыдущей работы либо не перезапущен текущий процесс. |
| В `.env` изменён порт, но он прежний | Файл не загружен: использовать `--env-file` или аргумент запуска. |
