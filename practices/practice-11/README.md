## 3. Окружение и подключение

### 3.1. Инструменты

Для работы используется PostgreSQL **18.x** и консольный клиент `psql`. Установщик выбирается для своей ОС на [официальной странице PostgreSQL](https://www.postgresql.org/download/). pgAdmin допустим для просмотра данных, но обязательные скрипты должны воспроизводиться через psql.

```bash
psql --version
```

Если команда не найдена, необходимо добавить каталог `bin` установленного PostgreSQL в PATH либо запускать psql полным путём. Для Windows путь при стандартном размещении может быть `C:\Program Files\PostgreSQL\18\bin\psql.exe`; фактический каталог следует проверить. В PowerShell запуск пути с пробелами выполняется через `&`:

```powershell
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" --version
```

Служба PostgreSQL должна быть запущена. Используются локальный адрес `127.0.0.1` и стандартный порт 5432; при другом порте он указывается явно в каждой команде.

### 3.2. Роль и отдельная учебная база

Подключиться к административной базе под установленной при настройке административной ролью. В стандартном примере это `postgres`:

```bash
psql -h 127.0.0.1 -p 5432 -U postgres -d postgres
```

Внутри psql выполнить **один раз**:

```sql
CREATE ROLE tip_app LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE;
\password tip_app
CREATE DATABASE tip_tasks OWNER tip_app ENCODING 'UTF8' TEMPLATE template0;
\q
```

Пароль задаётся через интерактивный запрос `\password`; он не записывается в SQL, README и Git. Имена роли и базы можно изменить, но тогда нужно согласованно изменить команды и указать их в отчёте. Если роль или база уже существует, не удалять её ради повторного запуска: сначала проверить назначение либо создать отдельную учебную базу с другим именем.

`CREATE DATABASE` выполняется вне транзакции. Если используется учебный сервер с ограниченными правами, преподаватель или администратор предоставляет отдельную базу и владельца; административные команды тогда не требуются.

Проверить подключение владельцем:

```bash
psql -h 127.0.0.1 -p 5432 -U tip_app -d tip_tasks
```

```sql
SELECT current_database(), current_user, version();
SHOW server_encoding;
SELECT lower('ПРОВЕР') = 'провер' AS russian_case_supported;
\q
```

Ожидаются выбранная учебная база, роль `tip_app`, UTF8 и `true` в проверке регистра. Поведение регистра зависит от локали базы. Если результат `false`, требуется база с локалью, поддерживающей кириллицу; менять исходные данные или ожидания поиска для сокрытия проблемы не следует.

### 3.3. Размещение и порядок команд

Перенести только `practices/practice-11/starter/practice-11` в корень личного репозитория. Все следующие команды выполняются из `practice-11`:

```bash
psql -X -h 127.0.0.1 -p 5432 -U tip_app -d tip_tasks -v ON_ERROR_STOP=1 -1 -f sql/01_schema.sql
```

Схема запускается в пустой базе, seed — в пустых таблицах. Повторное выполнение этих файлов в уже заполненной базе должно завершаться ошибкой, а не удалять накопленные данные. `IF NOT EXISTS` и `ON CONFLICT DO NOTHING` не требуются: они могут скрыть несоответствие структуры или набора.

Для проверки создания с нуля создать **вторую пустую учебную базу**, например `tip_tasks_test`, и повторить команды с `-d tip_tasks_test`. Автоматического DROP в комплекте нет.

## 4. Модель данных

Каждая задача относится ровно к одной существующей категории. Категория может иметь от нуля до многих задач. Название категории хранится один раз, а задача содержит её id; копировать название категории в каждую задачу не требуется.

### 4.1. Таблицы и ограничения

| Таблица | Поле | Тип и обязательные правила |
|---|---|---|
| `categories` | `id` | `integer GENERATED BY DEFAULT AS IDENTITY`, PRIMARY KEY, положительное значение. |
| `categories` | `name` | `text`, NOT NULL, UNIQUE, длина 1–100, без обычных пробелов по краям. |
| `tasks` | `id` | `integer GENERATED BY DEFAULT AS IDENTITY`, PRIMARY KEY, положительное значение. |
| `tasks` | `title` | `text`, NOT NULL, длина 1–100, без обычных пробелов по краям. |
| `tasks` | `completed` | `boolean NOT NULL DEFAULT false`. |
| `tasks` | `priority` | `text NOT NULL`, только `low`, `medium`, `high`; без значения по умолчанию. |
| `tasks` | `category_id` | `integer NOT NULL`, FK на `categories(id)`, `ON DELETE RESTRICT`. |

Создать индекс `tasks_category_id_idx` на `tasks(category_id)`. Внешний ключ не создаёт такой индекс автоматически. Для 12 строк ускорение измерять не требуется; индекс готовит доступ по категории к следующему этапу.

Требования к тексту выражаются через `char_length(value) BETWEEN 1 AND 100` и `value = btrim(value)`. Для пустой строки, пробелов и длины 101 ожидается ошибка. Ограничение **отклоняет** значение с пробелами, а не исправляет его; нормализация входа остаётся обязанностью приложения.

В этой учебной схеме `char_length` считает символы PostgreSQL, а JavaScript `.length` из ПР10 — единицы UTF-16. Например, для некоторых emoji результат различается. Кроме того, `btrim` без второго аргумента обрезает обычный пробел, а `trim()` JavaScript обрабатывает более широкий набор пробельных символов. Поэтому SQL-проверки не заменяют прежнюю API-валидацию; в ПР12 она сохраняется. Для обязательных исходных строк эти различия не влияют на результат.

UNIQUE имени категории сравнивает значение по правилам выбранной базы; отдельное регистронезависимое правило здесь не вводится. Названия задач могут повторяться.

### 4.2. Соответствие API

| JavaScript / JSON | PostgreSQL |
|---|---|
| `id` | `id` |
| `title` | `title` |
| `completed` | `completed` |
| `priority` | `priority` |
| `categoryId` | `category_id` |

В SQL используются имена `snake_case`. Внешний API сохраняет `categoryId`. Для будущей выдачи можно использовать `category_id AS "categoryId"`; двойные кавычки сохраняют регистр алиаса. Сам контракт JSON в этой работе не меняется.

Тип `integer` выбран для учебных id; он уже диапазона безопасных целых JavaScript. Диапазон положительных id базы — до 2147483647. Полную вместимость `Number.MAX_SAFE_INTEGER` этот выбор не обеспечивает; для данного набора она не требуется.

## 5. Теория

### 5.1. Ключи и ограничения

PRIMARY KEY идентифицирует строку. FOREIGN KEY связывает задачу с существующей категорией. CHECK проверяет условие для строки, а NOT NULL запрещает отсутствие значения. Для обязательного поля нужны обе проверки: CHECK сам по себе не запрещает NULL.

`ON DELETE RESTRICT` предотвращает удаление категории, на которую ссылаются задачи. Автоматическое удаление её задач в этой модели не требуется. Пустую категорию удалить можно. Подробнее: [PostgreSQL: Constraints](https://www.postgresql.org/docs/18/ddl-constraints.html).

### 5.2. Identity и исходные id

Identity назначает значение при INSERT без id. В режиме `BY DEFAULT` разрешено явно вставить прежние id из ПР10. У задач они разреженные: 1, 4, 7, …, 34. После загрузки необходимо синхронизировать последовательность с максимальным id. Явные вставки сами её не продвигают.

Функция `pg_get_serial_sequence('public.tasks', 'id')` возвращает имя связанной последовательности, несмотря на историческое название функции. `setval(sequence, maximum, true)` устанавливает состояние так, что следующий id будет больше maximum. Аналогичная настройка нужна категориям. В предоставленном непустом наборе максимумы равны 34 и 3; в решении их следует получать запросом `max(id)`, а не фиксировать числа.

После чистой загрузки первая обычная вставка даст задаче id 35 и категории id 4. После проверок точные значения могут быть больше. Подробнее: [Identity Columns](https://www.postgresql.org/docs/18/ddl-identity-columns.html).

### 5.3. Пропуски в id

Последовательность — не счётчик количества строк. Удаление, откат и неуспешная вставка могут оставлять пропуски. PostgreSQL не возвращает использованное значение nextval назад при ROLLBACK. Изменения setval тоже не отменяются откатом.

Это отличается от учебного массива ПР10, где валидация выполнялась до увеличения счётчика. В ПР12 нельзя требовать отсутствия пропусков или повторно назначать удалённые id. Подробнее: [Sequence Manipulation Functions](https://www.postgresql.org/docs/18/functions-sequence.html).

### 5.4. JOIN и агрегаты

INNER JOIN соединяет строки, для которых найдена пара. LEFT JOIN сохраняет все строки слева, даже если справа совпадений нет. Для подсчёта задач по категориям, включая пустые, нужен LEFT JOIN и `count(t.id)`: `count(*)` посчитает также строку категории без задачи.

WHERE фильтрует строки до группировки, HAVING — группы после неё. Для воспроизводимого порядка результата нужен явный ORDER BY. Порядок хранения строк не является гарантией порядка SELECT. Подробнее: [Joins Between Tables](https://www.postgresql.org/docs/18/tutorial-join.html).

### 5.5. Транзакция и воспроизводимость

BEGIN открывает транзакцию, COMMIT подтверждает изменения, ROLLBACK отменяет их. Неверный UPDATE с несколькими полями не должен частично изменить строку. Если в ручной транзакции произошла ошибка, дальнейшие команды обычно требуют ROLLBACK или возврата к заранее созданной точке сохранения.

Нумерованные SQL-файлы фиксируют порядок подготовки. Это ещё не полноценный инструмент миграций: здесь нет таблицы версий и автоматического обновления существующей базы. Изменение уже применённого файла не изменяет таблицы само по себе. Для текущей работы воспроизводимость проверяется повторным созданием в другой пустой базе.

## 9. Проверки

### 9.1. Автоматическая проверка схемы

На исходном наборе выполнить:

```bash
psql -X -h 127.0.0.1 -p 5432 -U tip_app -d tip_tasks -v ON_ERROR_STOP=1 -f checks/schema.check.sql
```

Скрипт проверяет структуру, начальные количества, identity, обязательность полей, PK, FK, ограничения текста и приоритета, индекс, фильтры, удаление категории и поведение при ошибках. Предусмотрена проверка допустимой вставки, DEFAULT completed и последующего id после удаления.

Проверки выполняются в транзакции и завершаются ROLLBACK. **Строки восстанавливаются, но последовательности могут продвинуться.** Поэтому после проверки не следует ожидать ровно id 35. Повторный прогон должен также проходить.

При успехе выводятся **41 строка PASS** и общий счётчик `passed: 41`. При первой неудаче выполнение останавливается с FAIL. Если запуск проводился вручную в уже открытой сессии и завершился ошибкой, выполнить ROLLBACK перед дальнейшими действиями.

Скрипт не проверяет текст Q1–Q7 и индивидуального SELECT: их результаты необходимо отдельно сравнить с таблицами методички. Наличие схемы не подтверждает выполнение запросов.

### 9.2. Транзакция

Запустить пример отдельно, **без `-1`**, поскольку он сам содержит BEGIN/ROLLBACK:

```bash
psql -X -h 127.0.0.1 -p 5432 -U tip_app -d tip_tasks -v ON_ERROR_STOP=1 -f examples/transaction.sql
```

Для задачи 4 ожидается: до изменения `false`, внутри транзакции `true`, после отката снова `false`. Объяснить, почему пример не меняет итоговые данные.

### 9.3. Ручной протокол

| № | Действие | Ожидаемый результат |
|---:|---|---|
| 1 | Проверить базу, роль, кодировку и регистр кириллицы. | Верные база/роль, UTF8, true. |
| 2 | Создать схему и загрузить seed. | 3 категории, 12 задач. |
| 3 | Посмотреть `\d` таблиц. | Все типы, DEFAULT, ограничения и индекс присутствуют. |
| 4 | Выполнить Q1–Q7 и вариант. | Совпадение с таблицами разделов 7–8. |
| 5 | Запустить автоматические проверки дважды. | Оба прогона успешны; исходные строки сохранены. |
| 6 | Выполнить пример транзакции. | Статус false → true → false. |
| 7 | Добавить пустую категорию в транзакции, выполнить Q4/Q5. | Категория присутствует с нулями; затем ROLLBACK. |
| 8 | Повторить создание в второй пустой учебной базе. | Та же структура и те же исходные данные. |
| 9 | Закрыть psql и подключиться снова. | Подтверждённые исходные данные сохранены. |

Перезапуск Express не влияет на SQL-базу; в ПР11 они ещё не связаны. Закрытие клиента psql не удаляет подтверждённые записи.

## 10. Типичные ошибки

| Проявление | Причина и исправление |
|---|---|
| connection refused | Служба не запущена либо неверный порт. |
| password authentication failed | Проверить роль, пароль и адрес сервера. |
| permission denied for schema public | Подключение не владельцем нужной базы; проверить current_user и владельца. |
| relation already exists | Схема повторно применяется в непустой базе; для проверки использовать новую базу. |
| В seed конфликт id | Набор уже загружен; не скрывать конфликт через ON CONFLICT. |
| Первая автоматическая вставка конфликтует с id 1 | Не синхронизирована identity-последовательность после явных id. |
| Пустая категория исчезла из отчёта | Использован INNER JOIN или условие WHERE убрало строки без задач. |
| Пустая категория имеет одну задачу | Использован count(*) вместо count(t.id). |
| Проценты всегда 0 или 100 | Целочисленное деление; нужен numeric. |
| Все команды после ошибки отклоняются | Транзакция находится в ошибочном состоянии; выполнить ROLLBACK. |
| После ROLLBACK id увеличился | Это штатное поведение последовательности, а не потеря строк. |
| В API осталось старое содержимое | Сервер ПР10 ещё использует память; подключение базы будет в ПР12. |
